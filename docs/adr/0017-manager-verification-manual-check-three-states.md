# 經理人驗證採人工核對加三態狀態機，不做自動化爬取

平台不得讓未驗證者以經理人身分簽章或代操作。可用管道中，resim 附圖形驗證碼，商工登記 API 的申請在 demo 階段跳過。決議：第一版由平台營運者人工核對，把結果寫成核對紀錄，再由狀態機轉移。系統不爬取 resim，也不繞過驗證碼。狀態只存三態，與 PRD 和第二輪報告 6.5 一致，不採架構 4.9 的六態。

## 決議內容

1. **核對管道。** `channel` 的值如下。狀態機與管道分開，所以換管道時狀態機不改。

   | `channel` | 用途 | 階段 |
   |---|---|---|
   | `gcis_manual` | 平台營運者查商工登記後登錄 | 第一版 |
   | `gcis_api` | 系統呼叫商工登記 API | MIL-49 核准後 |
   | `resim_manual` | 平台營運者查 resim 後登錄，含業者、證書與任職 | 第一版 |
   | `document_review` | 平台營運者核對文件 | 第一版 |
   | `resim_batch` | 批次核對 | 內政部地政司核准後 |

2. **商工登記第一版全部人工。** 依使用者 2026-11-07 的定案。月度重查由平台營運者人工執行，worker 每月產生佇列項目。商工登記 API 核准後改為自動，觸發條件是 MIL-49 完成。頻率「每月」是 PRD 的假設。

3. **三態。** 狀態只有 `pending`（待驗證）、`verified`（已驗證）、`lapsed`（已失效）。

   | 架構 4.9 的狀態 | 本決議 |
   |---|---|
   | `renewal_due` | 不存。由 `valid_until` 與查詢時點推導 |
   | `rejected` | 刪除。`pending` 加最新核對紀錄不符，就是待補件，符合 P0-04 AC2 |
   | `conflict_review` | 刪除。專任規則見決議 7 |

   被刪的 `rejected` 與 `conflict_review` 都不能簽章，與 `pending` 的行為相同。

4. **轉移表。**

   | 目前狀態 | 事件 | 條件 | 下一狀態 |
   |---|---|---|---|
   | 無 | `submitted` | 必填欄位齊全 | `pending` |
   | `pending` | `check_matched` | 核對相符，且不違反專任的排除約束 | `verified` |
   | `pending` | `check_mismatched` | 核對不符或查無資料 | `pending` |
   | `pending` | `resubmitted` | 補件 | `pending` |
   | `verified` | `renewed` | 新效期核對相符 | `verified`，更新 `valid_until` |
   | `verified` | `expired` | 查詢日晚於 `valid_until` | `lapsed` |
   | `verified` | `revoked` | 重驗發現廢止或與登錄不符 | `lapsed` |
   | `verified` | `registration_lost` | 業別層：登記狀態不是核准設立 | `lapsed` |
   | `verified` | `employment_ended` | 任職層：任職結束 | `lapsed` |
   | `verified` | `consent_ended` | 任職層：同意書撤回或到期 | `lapsed` |
   | `lapsed` | `resubmitted` | 換證或恢復登記 | `pending` |

   新任職建新列，已結束的任職不回到 `pending`。

5. **狀態放在三層。** 驗證狀態只放在業別（`practice_licenses`）、證書（`practitioners`）、任職（`practitioner_employments`）。執業主體本身不存狀態。理由：執業主體兼營代管與經紀時，代管失效不得影響經紀。登記狀態不是核准設立時，全部業別轉 `lapsed`。

6. **各層獨立核對。** 刪除架構的「上層也已驗證」條件，核對順序不受限。可簽章由 `credentialStatusAt()` 組合：對應業別、證書、任職都是 `verified`，且任職期間涵蓋查詢時點，且查詢時點不晚於 `valid_until`。§25 的「至少一位已驗證專任」是推導出的檢查，不是狀態。

7. **專任規則的四個判定點。**

   1. 建立任職時，系統同步判定：
      - 管理人員專任：別家已有 `verified` 在職時阻擋，不建列，訊息不揭露別家，並寫稽核紀錄。別家只有 `pending` 時允許並存。
      - 經紀人員：別家已有 `verified` 在職時提示，要求所屬業者的同意書，建 `pending`。
   2. 核對相符轉 `verified` 時，由排除約束擋住。約束只涵蓋 `verified`。平台營運者依 resim 任職查詢判定哪一家。
   3. 送簽與簽章當下，由可簽章判定。細節屬 MIL-46。
   4. 定期重驗時，resim 與登錄不符就轉 `lapsed`。

   允許 `pending` 並存的理由：否則 B 公司能先登錄 X 的證號，把真正的雇主鎖住。系統只回應登錄方，不通知另一家。同意書有效期由任職記錄。

8. **效期與換證。**

   - `valid_until` 由平台營運者依 resim 登錄。發證日加 4 年只用來預填與提示不一致。
   - 換證提醒在進入窗口當日與期滿前 30 日各一次，可設定。後者是假設。
   - 換證送審期間維持 `verified`，到舊的 `valid_until` 為止。未核對完就轉 `lapsed`，沒有寬限期。
   - 任職每 6 個月重驗，是架構的提議，可設定。
   - `credentialStatusAt()` 一定比對效期，所以 worker 失敗時也不放行。

9. **失效不回溯。** 已完成的合約不動（ADR-0006），`credential_snapshot` 凍結。簽署中的簽署任務，系統通知執業主體撤回後改派（P0-04 規則 9）。進行中案件的狀態不變，代操作動作停用，並提示移交（P0-22）。這與 MIL-42 的「權源失效自動撤回」不同，因為權源失效影響的是承租人該不該簽。

10. **核對紀錄。** `credential_checks` 是 append-only，更正只能新增一筆。

    | 欄位 | 說明 |
    |---|---|
    | `subject_type`、`subject_id` | 業別、證書或任職 |
    | `channel` | 見決議 1 |
    | `query_source` | 查詢的頁別 |
    | `observed` | 只放 P0-04 個資規則列的欄位 |
    | `result` | `match`、`mismatch`、`not_found`、`revoked` |
    | `evidence_version_ids` | 文件版本 |
    | `note` | 判定理由 |
    | `checked_by`、`checked_at` | 平台營運者與時間 |

    - 系統不存查詢頁截圖。
    - 影本放 `vault`。相符後刪除或遮罩。不符時保留到補件相符，或 30 日後刪除。30 日是假設。
    - 每筆核對紀錄同交易寫稽核事件。
    - 只有單人核對，不做雙人覆核。

11. **全域登錄。** 執業主體、業別、執業人員、任職、核對紀錄都放 `registry`，驗證狀態全域一份。

    - 證書層核對跨組織沿用。X 換公司時，平台營運者只核任職。
    - 只經定義者函式存取，回傳不得透露別的組織（ADR-0012 決議 8）。
    - 第二個組織認領同一統編時，系統送人工審核。
    - 屋主只拿到標章投影。標章文字固定為「證書資料已核對」加核對日。

12. **人力不是本決議的前提。** 依「只算系統開發」，系統只在審核佇列顯示等待時間。PRD 的 L1、L2 維持假設。待審件積壓超過 3 個工作天時重看。pilot 人力留在 MIL-35 的 Not yet specified。

13. **測試 seam。** `decideCredentialTransition(state, input)` 與 `credentialStatusAt(facts, at)` 是純函式，沿用 `decideTransition()`。時間一律由參數傳入。單元測試用狀態乘輸入的全矩陣表格。

## Considered Options

- **程式化爬取 resim：** 自動，但要繞過圖形驗證碼，平台不得這樣做。
- **只收證書影本，不核對：** 最省人力，但無法發現偽造或失效，也撐不起「證書資料已核對」標章。
- **等內政部核准批次核對再開通：** 自動且合法，但核准時間未知。
- **架構 4.9 的六態：** 畫面標籤可直接對應狀態。但與 PRD 的 AC 不符，P0-05 AC1 要同步阻擋，P0-04 AC2 要維持待驗證。多出的狀態行為也與 `pending` 相同。
- **排除約束涵蓋 `pending`：** 重疊在登錄時就擋下，但任何公司都能搶先登錄別人的證號。

## Consequences

- 畫面的細分標籤（待補件、換證提醒）必須推導，所以核對紀錄是必要資料。
- 平台營運者每月要人工重查執業主體，每 6 個月要重驗任職。
- 第一版的 P0-03 AC2 判定時點改為平台營運者登錄營業項目時，而非執業主體送出時。
- 兩家同時 `pending` 時，平台營運者要多判定一次。
- 審核積壓時，已換證的人員可能被暫時停權。
- 平台營運者的一次核對錯誤會影響所有組織，因為核對結果全域沿用。
- 舉證只靠結構化紀錄與核對者。截圖是否必要列入 MIL-62。
- 執業人員帳號的綁定流程留給 C 線 spec。
- 架構文件與 PRD 的待改項目列在 MIL-61。
