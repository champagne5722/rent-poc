# 案件用狀態表加事件表，不採全面事件溯源

一個租賃案件從擬約到押金結算，跨越出租人、承租人與經理人。現有 `transitions.ts` 只管單一合約。決議：案件用狀態表加 append-only 的案件事件，由純函式決定轉移，在同一交易寫入。案件只記錄流程進度。權源、押金與簽署進度各有自己的真相來源，案件不存第二份。

## 決議內容

1. **形式。** `cases.state` 是目前狀態，`case_events` 是發生過的事。`decideCaseTransition()` 回傳下一狀態、事件與 outbox 任務。`dispatch()` 在 `withTx` 內同一交易寫入，並以 `state_version` 做樂觀鎖。

2. **案件事件的範圍。** 案件事件只記案件的轉移與案件層動作，不抄合約歷程。理由同 ADR-0010 決議 11：同一份事件流水再存一次，沒有讀取者。

3. **租賃案件有七個狀態。**

   | 狀態 | 進入條件 | 下一狀態 |
   |---|---|---|
   | `draft` | 建立案件；合約撤回或拒簽 | `signing`、`aborted` |
   | `signing` | 合約送簽，前提檢查通過 | `active`、`draft` |
   | `active` | 合約全員完成；取消退租 | `move_out` |
   | `move_out` | 發起退租 | `settling`、`active` |
   | `settling` | 退租點交完成；或登錄催告後手動推進 | `closed` |
   | `closed` | 使用者結案 | 無 |
   | `aborted` | 送簽完成前放棄 | 無 |

4. **權源不是案件狀態。** MIL-42 決議待驗證得送簽，所以架構 4.3 的 `authority_verified` 不成立。權源狀態也會自己變動，存兩份會不一致。權源與委託檢查改為送簽前提，由 `checkSendPreconditions()` 回傳原因清單。

5. **押金不是案件關卡。** 案件不訂閱 `DepositConfirmed`，也沒有 `awaiting_deposit`。入帳確認靠使用者登錄或匯入對帳檔，押金得分次收取，應收期別在合約完成時就產生。如果把押金當關卡，使用者沒登錄時，入住點交與修繕都會卡住。押金進度由押金台帳投影。

6. **退租與結案。**

   - 退租點交完成的定義：自管是雙方確認，代管與包租是點交證明完成簽章。
   - 一方未會同時，使用者登錄催告後得手動推進到 `settling`。系統只記錄，不判定法律效果。
   - `closed` 由使用者觸發。Phase 1 不用 `DisbursementExecuted`，因為 P0-18 規定系統不產生撥款指示。
   - 下列任一項成立時，使用者必須填未結原因，系統必須寫稽核紀錄：押金餘額不為 0、押金結算單未完成、代管或包租的退還證明未完成。

7. **發起退租。** 出租人、委託範圍含點交的代管業者、包租業者得發起。承租人不得發起，實際通知在平台外。退租點交雙方確認前，發起者得取消，案件回到 `active`。

8. **租期屆滿不轉移。** worker 只提醒。續約屬 P1-05。P1-05 定案前，續約由使用者開新案件。

9. **委託管理案件。** 狀態是 `draft`、`signing`、`active`、`terminated`、`expired`、`aborted`。

   - 合約撤回或拒簽時回到 `draft`。
   - 上傳紙本契約書時，案件由 `draft` 直接進 `active`，事件是 `paper_contract_registered`。
   - 刪除 `management_contracts.status`，只留案件狀態。
   - worker 在 `valid_period` 屆滿時轉 `expired`。移交生效時，舊案件轉 `terminated`。

10. **移交不改租賃案件的狀態。** 移交只改業務類型或委託連結，並寫案件事件。有進行中的簽署任務時，系統必須擋下（P0-22 規則 2）。

    跨組織的情況由 ADR-0024 修正。

11. **單向投影。** 鏈條是簽署事件、簽署進度、合約狀態、案件狀態。

    - 案件是合約的訂閱者，與 ADR-0010 決議 8 在同一交易。`decideTransition()` 不知道案件存在。
    - 案件只認 `current_contract_id` 的送簽、全員完成、拒簽、撤回。案件不存簽署進度。
    - 案件拒絕某事件時，合約轉移照常提交，案件寫 `input_rejected` 事件並通知。法律事實優先。
    - `state_version` 衝突時整個交易回滾，由 webhook 的 inbox 重試。

12. **與 ADR-0006 相容。** 合約狀態只到 `completed`。退租、終止與結案都在案件層，所以合約不加 `expired`。撤回與拒簽的新草稿留在同一案件，衍生關聯的規則不變。合約完成後要改約時，Phase 1 沒有流程，由使用者開新案件。

13. **其他送簽文件不是合約。** 點交證明、押金結算單、退還證明不放 `contracts.doc_kind`。依 `GLOSSARY.md`，合約只有租賃合約與委託管理合約，這三種文件是獨立的簽署標的。案件訂閱它們的完成事件。資料表由 E 線 spec 決定。

14. **案件成員有八種關係。** 架構 4.5 與 PRD P0-09 的清單不同，本決議統一如下。

    | `relation` | 中文 | 備註 |
    |---|---|---|
    | `lessor` | 出租人 | 包租案件是包租業者 |
    | `lessee` | 承租人 | |
    | `co_lessee` | 共同承租人 | 權限同承租人 |
    | `mandator` | 委託人 | |
    | `mandatary` | 受託人 | |
    | `owner` | 所有權人 | 只用於包租案件 |
    | `practitioner` | 簽章人員 | 含專任管理人員與經紀人 |
    | `broker` | 經紀業者 | 只有讀合約與指派經紀人 |

    架構的 `practice`、`sublessor` 與上表重複。`reviewer` 刪除，因為平台營運者走審核佇列（ADR-0012 決議 5）。業務類型維持自管、代管、包租。居間是經紀業者加入案件，主辦組織仍是出租人或代管業者。

15. **成員讀取依關係過濾。** 架構的 `case_member_read` 不分關係，包租案件的所有權人會讀到合約，違反 P0-09 AC5。每張案件範圍表必須列出可讀的關係。

    - 沿用 ADR-0012 決議 7 的 `self_read`。
    - `owner` 只得讀 `cases`，所以 `cases` 必須有租期欄位。
    - 結案不結束 `valid_period`（P0-09 AC6）。唯讀由 `authorize()` 依案件狀態判斷。
    - 移交生效時，系統關閉舊受託人的 `valid_period`。

16. **成員寫入只有一個入口。** 承租人確認點交、標示異議、報修，以及屋主確認點交，都是寫入別的組織的資料表。`withCaseMemberTx` 依序執行下列步驟。

    1. 以 `app.party_id` 經 `self_read` 查成員資格。
    2. 由 `authorize()` 檢查關係、動作與案件狀態。
    3. 以案件的 `org_id` 執行 `set_config`。
    4. 執行固定的 repository 方法，同交易寫稽核紀錄。

17. **Phase 2 只留 seam。** Phase 1 的 `kind` 只有 `lease` 與 `management`，不建 `anchor_id`、`inventory_id`。`state` 存 text，加 `(kind, state)` 的 CHECK，不用 PostgreSQL enum。純函式依 `kind` 分派。買賣七段維持架構的提議，本決議不定案。`cases.trust_case_ref_id` 依 MIL-44 的決議。

18. **計時器由 worker 掃描。** Phase 1 共 7 條：委託到期、換證窗口、證書期滿、任職重驗、執業主體重查、點交 7 天提醒、逾期提醒。worker 每日執行一次，逐組織 `set_config`。冪等鍵是主體、事件與日期。觸發方式由 A 線 spec 決定，因為 Cloud Run 的 `min-instances=0` 需要外部觸發。

19. **測試 seam。**

    - `decideCaseTransition(snapshot, input)` 是純函式，不接受時回傳 `null`，沿用 `decideTransition()`。
    - `checkSendPreconditions(facts)` 是另一個純函式。時間一律由參數傳入。
    - 單元測試用狀態乘輸入的全矩陣表格。
    - `dispatch()` 的整合測試用 PGlite 與 `SET ROLE app_rw`（ADR-0012 決議 13）。
    - `waiting_on` 不存欄位，由純函式推導。

## Considered Options

- **全面事件溯源：** 歷史完整，能重建任意時點。但重播會重觸發對外訊息，讀端有延遲。案件的讀取需求多為目前狀態，所以這個能力的價值低。
- **外部工作流程引擎（例如 Temporal）：** 重試與補償機制完整，但多一套基礎設施。重看條件是買賣七段的計時器與補償規則超過 20 條。
- **照架構 4.3 保留 `authority_verified` 與 `awaiting_deposit`：** 案件清單能直接篩選。但前者與 MIL-42 矛盾，後者會讓人工登錄的缺漏卡住流程。
- **案件成員的 INSERT 與 UPDATE 政策：** 不用切換組織脈絡。但 RLS 不能限制欄位，承租人會能改租金。
- **案件成員寫入改用定義者函式：** FORCE 下函式 owner 也受 RLS 限制（ADR-0012 實測），查詢結果是空值。
- **把居間延到 Phase 2：** 不用多一種關係，但要改 P0-10 與 P0-12。

## Consequences

- 案件狀態看不出權源是否已驗證，也看不出押金是否已入帳。清單與畫面必須另查出租權源與押金台帳。
- 結案是使用者宣告，可能提早。未結原因與稽核紀錄是補償措施。
- 承租人不能在平台發起退租。續約時押金要手動處理。
- `withCaseMemberTx` 第 3 步之後，該交易看得到整個組織的資料。所以它只接固定方法，CI 滲透測試必須加這個案例。
- 經紀業者在 Phase 1 不能自己開案件。
- 新增案件範圍表時，必須逐表寫 RLS 政策。
- Phase 1 沒有不可回頭步驟。這個分類保留給 Phase 2 的撥款執行與地政登記。
- 「謄本仍新鮮」在 PRD 沒有定義，不列入送簽前提，由 B 線決定。
- 查詢委託是否有效時必須 join 案件。
- E 線必須另建點交證明、押金結算單與退還證明的實體。
- `dispatch()` 依賴 `withTx` 與 outbox，所以 C 線必須等 A 線。
- **延伸 ADR-0010：** 合約的訂閱者多一個案件，同交易範圍加上案件狀態與案件事件。
- **延伸 ADR-0012：** 決議 5 的無組織脈絡入口多一個案件成員寫入。決議 7 的成員讀取依關係過濾。
- 架構文件與 PRD 的待改項目列在 MIL-61。

## 編號對應

本 ADR 對應架構文件第 8 節的候選 ADR-0013。正式編號 0013 是產權錨點，0014 與 0015 是金流（MIL-44），所以本 ADR 取 0016。
