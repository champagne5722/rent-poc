# 鏡像帳先於案件落地，入帳配對靠匯款識別，月報表存快照

ADR-0014 與 ADR-0015 定了鏡像帳的規則。它們留下四件事給 E 線：匯款識別、社宅屬性的標記、`ledger` 模組介面、押金台帳的建立時點。另外，鏡像帳以 `case_id` 連到案件，而案件屬 C 線，C 線的 spec 還沒發。決議：E 線拆成兩張 spec，帳務先做。鏡像帳的表先建，`case_id` 先不掛外鍵。入帳配對只在條件全部明確時寫分錄。屋主月報表產出時存完整快照。

## 決議內容

1. **E 線拆成兩張 spec。** 主控對話與整合分支 `integration/line-e` 不拆。

   | spec | P0 | 主要依賴 |
   |---|---|---|
   | E1 帳務 | P0-13、P0-14、P0-15、P0-19 | A 線的 PostgreSQL、outbox、worker route |
   | E2 租期中與退租 | P0-16、P0-17、P0-18、P0-21 | E1 的押金台帳、C 線的登入與案件成員、D 線的規則表 |

   承租人端不單獨拆。承租人的寫入動作是確認點交、標示扣抵異議、報修，這些實體都屬 E2。

2. **鏡像帳先於案件落地。** 鏡像帳的表與觸發器只等 A 線的 MIL-83。`case_id` 先存 `text`，不掛外鍵。到 `cases` 的複合外鍵由「接上案件」那張票以 `ADD CONSTRAINT` 加入。`ADD CONSTRAINT` 不改既有列，所以不違反只增不改。

   - 不做「先掛合約、之後改掛案件」的過渡。分錄只增不改，事後改欄位等於繞過觸發器。
   - E 線不建案件表。需要案件、案件成員或合約完成事件的票，必須等 C 線的租賃案件票。

3. **`ledger` 模組介面。** 只有 `ledger` 模組能呼叫 `postJournal()` 與 `reverseJournal()`（ADR-0015 決議 13）。其他模組只呼叫業務函式。

   | 業務函式 | 寫入的事件 |
   |---|---|
   | `confirmReceipt(tx, candidate)` | `receipt_confirmed`，含超額的預收 |
   | `applyPrepaid(tx, input)` | `prepaid_applied` |
   | `recordDepositDeduction(tx, input)` | `deposit_deducted` |
   | `recordDepositReturn(tx, input)` | `deposit_returned` |
   | `recordFundsHandover(tx, input)` | `funds_handed_over` |
   | `reverseEntry(tx, input)` | `reversal`，並讓配置失效 |

   讀取用 `depositBalance()`、`periodStatuses()`、`fundStatus()`。期別狀態與配置是純函式。

4. **押金台帳與應收期別在合約全員完成時建立。** 同一交易建立押金台帳與全部應收期別。約定金額取合約欄位的押金。

   - 全員完成前不開放手動登錄押金。
   - 全員完成前到的對帳檔列進待配對清單，標示「合約尚未完成」。

5. **應收期別的切法。** 一個月一期，到期日是該月的付款日，該月沒有那天時取月底。首末期不足一個月時依日數比例計算，四捨五入到元。按比例是假設，待訪談驗證。提前終止時，終止日之後的期別改 `cancelled`。終止日所在的期別不自動調整金額。

6. **匯款識別。** 每個租賃案件得登錄 0 到多筆匯款識別，內容是付款人戶名或付款帳號末五碼。對帳檔的列只在下列條件全部成立時寫分錄：

   - 收款帳戶與檔案匯入的帳戶相同。
   - 匯款識別命中恰好一個案件。
   - 用途能判定。押金未收足且金額等於差額時是押金。押金已收足時是租金。
   - 押金帳戶規則不是 `block`。
   - 沒有命中跨來源重複的條件（ADR-0014 決議 8）。

   其他情況一律進待配對清單。配對是純函式 `matchStatementRow(row, facts)`，回傳案件與用途，或回傳進清單的原因。

7. **欄位對應存在收款帳戶上。** 每個收款帳戶存一組 CSV 欄位對應。同帳戶之後的匯入自動套用。編碼接受 UTF-8 與 Big5，日期接受西元與民國年。

8. **待配對清單的處理。** 每列有四種處理：

   | 處理 | 結果 |
   |---|---|
   | 指定案件與用途 | 寫入確認。得拆成多個案件，金額合計必須等於該列 |
   | 與既有手動登錄是同一筆 | 不寫分錄，入帳確認記下佐證的列 |
   | 不是租賃款項 | 必須填原因，不寫分錄 |
   | 維持待處理 | 不變 |

9. **收款帳戶有分錄後不得改持有人。** 科目編碼用收款帳戶 ID（ADR-0015 決議 2）。持有人事後被改，既有分錄的資金位置就失真。要改時停用舊帳戶，新增一個帳戶。系統為每位持有人提供一個現金收取帳戶。

10. **社宅屬性是案件上的旗標。** 主辦組織在建立租賃案件時標記。有委託管理合約時，預設帶入該合約的設定。屋主看得到這個旗標。

    - 事後得修改。必須填原因，同交易寫稽核紀錄並通知委託人。
    - 改為社宅後，既有押金分錄不變。畫面列出持有人與規則衝突的提示。之後的押金入帳照新規則檢查。
    - 改為非社宅時，已被擋在待配對清單的列不自動釋放。
    - 欄位由「接上案件」票以 migration 加到 `cases`，不另開表。

11. **押金帳戶規則有版本。** `control.deposit_holder_rules` 由 migration 寫入，每列有 `rule_id` 與版本。修法時新增新版本的列取代舊列。系統提供「列出受影響案件」的查詢函式。Phase 1 不做管理畫面。

12. **通知模組。** 目前程式碼沒有寄信能力，也沒有站內通知。E1 建 `notify()`，同交易寫站內通知列與 outbox 的 email 列。

    - 寄信走 `Mailer` seam。第一版只有 Mock adapter，寫入可查詢的寄件紀錄。
    - 真實寄信服務商要選型，也可能付費，列為上線閘門，不在本決議。
    - 其他線的通知沿用 `notify()`。

13. **逾期與繳租提醒。** 逾期由 `scan-timers` 每日判定（ADR-0020）。寬限天數由組織設定，預設 3 天，預設值是假設。

    - 同一期別每天最多通知一次。對象是出租人與委託範圍含收租的代管業者。
    - 「發送繳租提醒」每按一次寄一封給承租人，寄件名義是該組織。24 小時內再按要確認。
    - 系統不排程寄信給承租人（MIL-42 Q1）。

14. **屋主月報表存快照。** 報表的單位是屋主乘產出組織乘月份（MIL-47）。

    - 月份結束後，由產出組織手動產出。
    - 產出時存完整的報表快照與 PDF 雜湊。差額說明在產出畫面填寫，存進快照。
    - 快照不得修改。之後的更正出現在下一份報表的沖銷列。
    - 得重新產出第 2 版。舊版保留並標示「已被取代」。必須填原因並寫稽核紀錄。
    - 代收的押金在 `funds_handed_over` 之前留在「需要留意」區段。
    - Phase 1 的代付沒有鏡像帳事件，報表不列代付明細。

15. **月報表的 CSV 結構。** 一份報表一個 CSV。編碼 UTF-8 加 BOM，讓 Excel 直接開啟。採長格式，每一列一行。

    | 欄位 | 內容 |
    |---|---|
    | 區段 | 摘要、需要留意、租金、押金、修繕、代收代付與交付、入帳與沖銷明細、來源比例、註記 |
    | 租賃單位 ID、門牌 | 摘要與註記為空 |
    | 項目 | 該區段的欄位名稱或事件類型 |
    | 日期 | 入帳日、交付日或期別到期日 |
    | 金額 | 整數新台幣元 |
    | 來源 | `manual`、`statement_file`、現金收取 |
    | 標示 | 逾期、逾 5 日、逾約定日數、已被沖銷 |
    | 說明 | 差額說明、確認者、備註 |

16. **測試 seam。**

    - 純函式：`matchStatementRow()`、`evaluateHolderRule()`、期別切分、期別狀態、配置、報表彙總。規則類函式用表格窮舉。
    - 性質測試：隨機事件序列後每筆分錄平衡，餘額等於手算結果（ADR-0015 決議 13）。
    - 整合：業務函式加 PGlite，每個測試 `clone()` 後 `SET ROLE app_rw`。
    - CSV 解析用 fixture，涵蓋 Big5、民國年、出帳列與重複匯入。

## Considered Options

- **不拆，一張 spec 八條 P0：** 少一張 spec，但承租人端與文件要等 C、D 線，帳務的票會被一起卡住。
- **拆成「帳務與文件」加「承租人端」：** 承租人端畫面集中，但點交與修繕的承租人動作會跨兩張 spec。
- **鏡像帳先掛合約，之後改掛案件：** 不必等 C 線，但只增不改的表無法改欄位。
- **E 線自己建案件表：** 不必等 C 線，但會在 C 線 spec 前定案案件結構，與 ADR-0016 衝突。
- **金額相符就自動配對：** 自動化程度高，但同額的兩個案件會配錯，錯了要沖銷再重登。
- **社宅屬性放在委託管理合約：** 少一個欄位，但沒有委託管理合約的紙本委託案件會漏標。
- **月報表每次開啟時即時計算：** 不必存快照，但違反 P0-19 的「產生後不可變」。
- **月報表完全不能重新產出：** 最嚴格，但差額說明打錯時沒有出口。
- **月報表 CSV 每區段一個檔，打包成 ZIP：** 每個檔欄位較少，但交付與開啟都多一步。
- **各線自己寫寄信：** 不必等 E1，但會有多套重試與紀錄。

## Consequences

- E1 的部分票要等 C 線的租賃案件票。C 線 spec 發佈後，E 線主控補上依賴。
- 「接上案件」之前，`case_id` 沒有外鍵保護。這段期間只有測試資料。
- 對帳檔的自動配對率取決於使用者是否登錄匯款識別。沒登錄時，所有列都進待配對清單。
- 使用者改持有人時要新增帳戶，舊帳戶的分錄留在原處。
- 社宅屬性標錯時，既有分錄不改，只靠提示與通知補救。
- 重新產出的月報表可能讓屋主拿到兩版。舊版必須清楚標示已被取代。
- demo 不會真的寄信。寄信服務商的選型是上線閘門。
- 修法改規則時，平台營運者不能自己改，要跑 migration。

## 編號對應

0019 與 0020 屬 A 線，0021 屬 D 線，所以本 ADR 取 0022。本 ADR 延伸 ADR-0014 的 Action Item 1 與 ADR-0015 的 Action Item 2。
