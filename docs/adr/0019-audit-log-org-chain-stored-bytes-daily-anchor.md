# 稽核紀錄每組織一條鏈，雜湊算在存下來的位元組，每日錨定

P0-23 要求平台側的稽核紀錄能發現竄改。ADR-0007 把這項工作列為新範圍，所以需要新決議。決議：每個組織一條稽核鏈，雜湊算在寫入時存下的文字上。鏈頭每日組成 Merkle 樹根，送到平台外服務取得回執。第一版的回執來自 FreeTSA，pilot 前換 TWCA 或中華電信。

本決議補充 ADR-0007，不取代它。合約歷程仍是活動時間軸，簽署舉證仍是 Audit Trail File。

## 決議內容

1. **範圍。** 稽核紀錄、合約歷程、案件事件是三種紀錄，互不抄寫。事件類別依 PRD P0-23 與架構 4.7。

2. **鏈的範圍。** 鏈由當下的 `app.org_id` 決定，呼叫端不得傳入。沒有組織脈絡時寫平台組織的鏈。

   | 情境 | 寫在哪條鏈 |
   |---|---|
   | 組織成員的操作 | 該組織 |
   | 平台營運者存取組織資料 | 目標組織，所以 P0-23 AC6 的匯出看得到 |
   | 案件成員寫入（ADR-0016 決議 16） | 案件所屬組織 |
   | 平台營運者的 `registry` 核對、承租人登入 | 平台組織 |

   本決議修訂架構 3.21 的「平台審核員的動作記在 `platform` 組織的鏈上」。

3. **寫入。** `audit.append()` 是定義者函式，與業務資料同交易。交易回滾時，序號不推進。函式鎖住鏈頭，鎖持續到提交。

4. **雜湊格式。**

   - `hash = sha256(prev_hash || canonical)`，以十六進位小寫存放。每條鏈的第一筆 `prev_hash` 是 64 個 `0`。
   - `canonical` 是寫入當下由資料庫產生的 JSON 文字，存成 `text` 欄位，內含 `v`、鏈、序號、時間、行為者、動作、物件與 `payload`。
   - 時間固定輸出成 UTC 的 `YYYY-MM-DDTHH:MM:SS.ffffffZ`。
   - 驗證時對存下來的位元組重算，並比對各欄位與 `canonical` 的內容。

   不在驗證時重新序列化。`timestamptz` 轉文字會跟著 session 時區改變，`jsonb` 的文字順序也不是 PostgreSQL 的正式保證。

5. **不放完整個資。** `payload` 只放變更前後的關鍵欄位。`canonical` 寫入後刪不掉，所以個資不得進入。保存期限依 Q16，列在 MIL-62。

6. **角色。** `audit` 的表與函式由 NOLOGIN 角色 `audit_owner` 擁有，沒有 `BYPASSRLS`。

   - 事件表與鏈頭表都設 FORCE。`audit_owner` 有自己的政策，否則函式會被 RLS 擋下。
   - `app_rw` 對事件表只有 SELECT，由 `chain_id = app.org_id` 的政策限制。
   - `app_rw` 對鏈頭表沒有權限。
   - UPDATE、DELETE、TRUNCATE 都由觸發器禁止，`audit_owner` 也一樣。

7. **錨定週期是每日。** 採 PRD P0-23，架構 4.7 的每小時由 MIL-61 修正。MIL-50 指出週期只縮短未錨定窗口，不縮短偵測延遲，因為 `verifyChain()` 每日才比對。沒有新事件的鏈不產生葉。全部的鏈都沒有變動時，不呼叫外部服務。週期是排程設定，改週期不用改程式碼。

8. **錨定內容。** 葉是鏈、序號、鏈頭雜湊。葉排序後組成 Merkle 樹，只送樹根。葉與回執都存在 `audit`，所以單一組織的鏈能獨立驗證。Merkle 計算是純函式。

9. **`AnchorProvider` 有兩個 adapter。** 介面只有取得回執與驗證回執。Mock 給測試用，FreeTSA 給 demo 用。RFC 3161 的請求與回執格式與 TWCA、中華電信相同，pilot 前只換端點與憑證。

10. **錨定失敗時，稽核寫入繼續。** 寫入不依賴外部服務。下一次排程會把未錨定的鏈頭一起送出。連續 2 次失敗時，系統寫 error 等級 log。

11. **不做副錨。** 第一版只有一個錨定服務。

12. **錨定的目的是偵測竄改。** 它不是訴訟證據。時戳的舉證力待法務確認，列在 MIL-62。

13. **`verifyChain()`。** 每日逐組織 `set_config`，重算該組織的鏈，再比對已存的葉與回執。不一致時寫最高等級 log。驗證工作不需要跨組織的讀取權限。

## 實測結果

環境是 PGlite 0.5.15，回報 PostgreSQL 18.6，日期 2026-11-08。沒有在 Cloud SQL 或 Neon 重跑。併發沒有測，因為 PGlite 只有單一連線。

| 情境 | 結果 |
|---|---|
| 同一時間，session 時區改成 UTC 與 `Asia/Taipei` | `timestamptz::text` 與 `to_jsonb` 的文字都不同 |
| FORCE，沒有 `audit_owner` 政策時呼叫 `audit.append()` | 被 RLS 擋下 |
| 加上政策後，A、B 兩組織各自寫入 | 序號各自遞增 |
| 沒有組織脈絡，或 `app.org_id` 是空字串 | 寫到平台組織的鏈 |
| 交易回滾後再寫入 | 序號沒有跳號 |
| `app_rw` 直接 INSERT、UPDATE、DELETE、TRUNCATE 事件表 | `permission denied` |
| `app_rw` 讀鏈頭表 | `permission denied` |
| `app_rw` 在 A 組織脈絡讀事件表 | 只有 A 的列 |
| `app_rw` 沒有組織脈絡讀事件表 | 0 筆 |
| `audit_owner` 的 UPDATE、TRUNCATE | 觸發器擋下 |
| Node 重算資料庫內 `sha256` 產生的鏈 | 一致 |
| 超級使用者關閉觸發器，只改欄位 | 驗證發現欄位與 `canonical` 不符 |
| 超級使用者改 `canonical`，不重算 | 驗證發現斷鏈 |
| 超級使用者重算整條鏈與鏈頭 | 本地驗證通過，鏈頭與舊值不同。這一項只有外部回執抓得到 |

FreeTSA 的呼叫沒有實測，RFC 3161 的 adapter 由 A 線實作時驗證。

把這些情境轉成測試時，每次 `clone()` 後都必須重新 `SET ROLE app_rw`（ADR-0012 Action Items 第 5 項）。

## Considered Options

- **驗證時重新序列化：** 不用多存一欄，但雜湊會跟著 session 時區與 PostgreSQL 版本改變。
- **全平台一條鏈：** 實作簡單，但所有組織的稽核寫入都要排隊，也無法單獨搬走一個組織的鏈。
- **平台營運者的動作都寫平台鏈（架構 3.21）：** 平台營運者的紀錄集中，但組織匯出時看不到別人存取自己的資料。
- **每小時錨定（架構 4.7）：** 未錨定窗口較短，但偵測延遲不變，而且每天要多喚醒 23 次。
- **第一版只做本地鏈，外部錨定只留介面：** 不用處理 ASN.1，但 P0-23 AC3、AC4 無法在 demo 走完。真實回執格式也要等到 pilot 才驗證。
- **FreeTSA 當正式主錨：** 免費，但沒有 SLA，營運者資訊也不透明（MIL-50）。
- **OpenTimestamps 或 S3 Object Lock 當副錨：** 能降低單一供應商風險，但第一版沒有需要它的情境。

## Consequences

- 同一組織的稽核寫入會排隊到提交。交易必須短，ADR-0012 決議 10 已禁止交易內的外部呼叫。
- 最長 24 小時內的竄改，只靠回執抓不到。下一次錨定會把竄改後的鏈頭當成正確值。比對舊回執時，只有已錨定的部分能被證明。
- demo 的回執沒有 SLA，FreeTSA 中斷時會連續失敗。pilot 前必須選定主錨，這是上線閘門。
- 每筆事件多存一份 `canonical`。300 個租賃單位的量不構成問題，Phase 1 結束前要依實際量再確認。
- `verifyChain()` 每次都重算整條鏈。事件量變大時，要改成從上次驗證點開始。
- 架構文件的待改項目列在 MIL-61。

3. 真實 PostgreSQL 容器測併發寫入同一條鏈。
