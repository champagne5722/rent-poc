# 合約文件三層組裝：主約鎖定、補充合約自訂、附件系統產出

商業目標是讓使用者有彈性調整合約，但整份開放編輯會讓「經法務審閱的公版」保證失效。決議（2026-08-02 grilling session）：合約文件由三層組成，彈性分層給——

1. **主約**：範本條款＋欄位值＋選用條款，條款文字平台鎖定，維持 ADR-0004／0005 原則不動。
2. **補充合約**：房東自訂自由文字的獨立頁，支援 `{{合約變數}}`（對應合約欄位，產出時以該約欄位值解析；有未解析變數不可送簽）。位於主約條款之後、簽署欄之前。取代 ADR-0005 所述「其他約定事項」條文欄（`ContractFields.extra` 退場，舊資料讀入為補充合約內容）。
3. **附件**：系統由結構化資料產出的表單頁。首個是**設備附件**（每列：項目＋數量＋修繕責任＋備註），建約時由物件設備清單帶入、逐約調整、送簽隨合約凍結為快照。呼應內政部 113 年版範本「本文勾有／無、清單放附件一」的寫法。

連帶決議：主約附屬設備條文由「列舉設備」改為「詳如附件『附屬設備清單』」，範本升版 v1→v2，第一次實際使用 ADR-0005 的草稿升版提示流程。設備詞彙由房東層**設備詞彙庫**（平台預設＋自訂）統一管理；修繕責任只存在合約層（內政部第八條預設出租人修繕，逐約例外）。

## Considered Options

- **整份文件開放編輯（文件編輯器＋變數）**：彈性最大，但法務保證消失、需以文件編輯引擎取代現行程式排版的 PDF 產出，工程與法律風險都大。否決。
- **只給 `extra` 欄位加變數支援**：改動最小，但自訂文字混在公版條款中，使用者與簽署方無法分辨哪些字經過法務審閱。否決。
- **設備清單續寫在主約本文**：免升版，但同一份合約兩處列設備、易不同步，法律文件忌諱。否決。

## Consequences

- Property 的設備清單由 `string[]` 升級為「項目＋數量」；新增房東層設備詞彙庫實體。「物件欄位以餵資料給合約為限」的 PoC 邊界自此開始鬆動（產品階段）。
- ContractFields：`extra` 退場、新增補充合約內容與設備附件列快照；範本 v2 與 v1 並存，舊合約因快照不受影響。
- PDF 產出新增補充合約頁與設備附件頁；簽署欄維持「一律另起一頁」，簽名框預設落點推導（`pdf-layout.ts`）不變。
- 現況確認書欄位群、設備照片、資產個體管理（序號／維修史／跨物件調度）皆為後續題目，設備附件的產製機制是它們的地基。
