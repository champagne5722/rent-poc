# 產權錨點以複合鍵唯一、ULID 當主鍵，租賃單位 ID 跨組織永久有效

> 2026-11-10：用詞與決議 9 已由 ADR-0027 修訂。「產權錨點」讀作「物件」，各組織的「物件」讀作「營運資料」。

現有 `properties` 只有名稱與地址，無法判斷兩筆物件是否為同一產權。門牌同址多戶且會整編，建號只在段小段內唯一，分租房間沒有官方識別碼。決議：產權錨點以五欄複合鍵做全平台唯一，主鍵用 ULID，放在全域登錄。租賃單位的 ID 由平台發行，換經理人與合併後都持續有效。全域登錄的存取規則見 ADR-0012。

## 決議內容

1. **唯一鍵。** 產權錨點的唯一鍵是縣市、鄉鎮市區、段小段、建號、分號五欄。沒有分號存 `000`。唯一索引只涵蓋 `pending_verification` 與 `keyed` 的錨點，沒有建號的錨點不受約束。

2. **欄位格式。** `section_code` 用 `text`，不固定位數。臺北市的編碼是 1 至 4 位，雲林縣西螺鎮是 4 位。行政區由編碼表帶出，使用者不得自行填寫，避免同一建物因行政區填法不同而變成兩筆。

3. **錨點狀態。** 狀態是 `pending_verification`、`keyed`、`merged`、`retired`。架構 3.7 的 `verified` 改為 `keyed`，因為建號由使用者填寫，平台沒有驗證。這也對齊 PRD P0-06 的「已建號」。

4. **分租的輔助鍵（Q19）。** 電號與水號不當輔助鍵，不進唯一鍵，Phase 1 也不收。平台無法驗證這些號碼。軟性層維持比對門牌、座標、樓層、房號。

5. **租賃單位主鍵。** 主鍵用平台發行的 ULID，無語意，永不重用。主鍵不含錨點 ID，因為待驗證錨點之後可能合併。

6. **單位後綴。** 單位後綴由平台依錨點發序號：`0000` 是整戶，分租單位從 `0001` 起。房號只放 `label`。理由是同一房間可能有不同房號：A 組織標「301」，B 組織標「3F-1」，用房號當後綴會產生兩個都合法的單位。房號改名時，鍵也不用改。

7. **顯示編碼。** 對外顯示編碼不得含完整建號（R13）。架構 3.8 的「錨點編碼加後綴」不再適用，格式由 B 線 spec 決定。

8. **合併。** 租賃單位加 `merged` 狀態與 `merged_into_id`，與錨點相同。待驗證錨點併入既有錨點時，兩邊都可能有 `0000`，會撞 `UNIQUE (anchor_id, suffix)`，所以單位也要能合併。規則如下：

   - 只有平台營運者能執行合併，每次都必須寫稽核紀錄。依 P0-06 AC3，系統不得自動合併。
   - 被併入的 ID 持續有效，讀取時解析到存續單位。
   - 合約快照保留原 ID。
   - 同一組織對兩筆單位各有物件時，審核流程必須一併處理物件。

9. **跨組織身分。** 換經理人時，新組織建立自己的物件，指向同一個租賃單位 ID。`registry` 函式只回傳呼叫組織有出租權源的資料。實測：定義者函式讀出租權源時，RLS 依呼叫組織篩選，不需另寫條件。

10. **主要出租權源。** 依 P0-07，同一租賃單位同一時間只能有一筆有效的主要出租權源。這條約束用部分唯一索引實作。唯一索引穿透 RLS，所以跨組織也成立。應用程式必須把這個錯誤轉成 P0-07 AC1 的訊息，不得顯示原始錯誤。

11. **外鍵。** `org` 的表到 `registry` 建外鍵。架構 3.2 的「不建跨 schema 外鍵」不採用。實測：`app_rw` 沒有 `registry` 權限也能寫入有效 ID，無效 ID 被擋下。`registry` 的列不會硬刪除，只會封存或合併，所以外鍵不會阻擋正常操作。

## Considered Options

- **複合鍵當主鍵：** 簡單，但待驗證錨點沒有建號，重測後建號會變，外鍵要全改。
- **門牌當主鍵：** 使用者容易提供，但同址多戶，整編會變。
- **每組織各自的錨點表：** RLS 一致，但同一建號在不同組織各一筆，移交與重複偵測失效。
- **房號當後綴（架構 3.8、PRD P0-06）：** 使用者看得懂，但無法分辨同一房間的不同房號，改房號要改鍵。
- **電號、水號當輔助鍵：** 能增加比對訊號，但平台無法驗證號碼是否屬於該房間。
- **不建跨 schema 外鍵（架構 3.2）：** 搬到組織專屬資料庫時不用改 schema，但 Phase 1 失去寫入時的完整性檢查。企業版尚未確定需求。

## Consequences

- PRD P0-06 的「分租單位以房號為後綴」要改。房間的重複偵測全靠軟性層。PRD 已寫明分租單位的偵測最弱，由出租權源補強。
- 搬到組織專屬資料庫時，必須移除到 `registry` 的外鍵，架構 4.4 的「schema 完全相同」不再成立。`registry` 函式讀 `org` 的出租權源，這個依賴也要改。
- 使用者填錯建號時，會佔住別人的唯一鍵。對方會收到 P0-07 AC1 的訊息，由平台營運者審核。

## Action Items

下列三題是 B 線 spec 前的 research，不在 MIL-43 解。

1. 查全國段碼的來源。目前只讀到各縣市自行發布的編碼表，沒有查到全國統一的表。
2. 查段代碼的唯一範圍，包括同一段是否跨行政區。臺北市的 CSV 人工掃描約一千筆，沒有看到同一編碼跨行政區。如果其他縣市有跨區的段，唯一鍵的欄位可能要改。
3. 查分租房間是否常有獨立電號。這點未查證，也不影響決議內容 4。

## 編號對應

本 ADR 對應架構文件第 8 節的候選 ADR-0014。架構 7.2 決策 5 的選項 A 不變。決議內容 3、6、7、8、11 修訂架構 3.2、3.7、3.8。
