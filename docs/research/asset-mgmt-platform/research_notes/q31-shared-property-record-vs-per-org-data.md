# Q31：同一個房子與多個組織有關時，房子的資料放哪裡、誰看得到什麼

> 法律判斷必須由法務確認。本筆記只查原文與官方說明，不下法律結論。
> 查閱日期：2026-11-10。
> 對應：ADR-0013 決議 5、9、ADR-0024 決議 2、6、ADR-0025、ADR-0026 決議 4、PRD P0-06、P0-07、P0-08、P0-09、P0-11、P0-22。
> 信心標記：【高】讀到官方原文；【中】只讀到搜尋摘要、第三方整理或第二手轉述；【低】推論。
> 用詞：本筆記一律用「物件」稱全系統唯一的房子（舊文件稱產權錨點）。「租賃單位」是物件底下能單獨出租的單位。各組織對租賃單位自存的資料稱「營運資料」（程式碼是 `org.properties`，舊文件也叫「物件」）。

## 結論

1. 查到的產品沒有一家讓兩個互不隸屬的管理公司共同讀寫同一份房子的營運資料。單一管理公司的軟體把房子放在公司帳號內。屋主是房子上的聯絡人或受限使用者。
2. 同時有屋主帳號與多家管理公司帳號的產品（Arthur、WealthPark）把「人」連起來，不把房子的資料合併。屋主用一個登入看到多家公司，但每家公司的帳務、對話、文件只給該公司。
3. 「全平台唯一的房子」只出現在識別碼層：RESO 的 UPI、英國的 UPRN、Zillow 的房屋頁。識別碼唯一，各來源的資料各存各的。這與 ADR-0013 的物件加租賃單位一致。
4. 產品負責人的直覺只有一半被支持。「物件只有一筆」已經成立，rent-poc 現況就是。「委任決定誰看到什麼」有證據，Airbnb 的 co-host 與 Hostaway、Guesty 的屋主入口都是由一方授權。「委任期間受託人讀寫共用資料，委任結束就失權」查不到任何產品這樣做。
5. 推薦方案丁：維持方案甲的資料歸屬，委任（委託管理案件）當獨立關係，屋主經這個關係讀指定欄位。換業者時設備與屋況經移交包複製帶走。改動量是「加欄位與讀取權限」，不改資料表歸屬。

## 0. 來源限制

1. Buildium 官方開發者站與說明中心抓取失敗（內容過大、302、載入錯誤）。Buildium 的欄位來自第三方 Ruby 套件文件，標【中】。
2. Guesty 與 Hostaway 的說明中心文章抓取回 403。本筆記用兩家的官方功能頁，標【高】但內容偏行銷。
3. AppFolio、Yardi、Propertyware、Rent Manager、DoorLoop API、PropertyMe、Console Cloud 沒有讀到可用的資料模型文件。列入未查證。
4. Airbnb 的 co-host 說明從搜尋摘要與一次成功抓取得到。頁面編號 1534。
5. 台灣的 JGB、591、樂租、好房網與內政部系統查不到公開的資料模型或授權文件。列入未查證。
6. 「換業者時資料怎麼走」查不到任何一家的官方移轉流程。這是本筆記最弱的一節。

## 1. 子題一：一筆還是多筆

### 1.1 房子放在管理公司的帳號內（單一管理方軟體）

**做法。** 房子（property）與底下的單位（unit）是管理公司帳號內的紀錄。屋主是另一種紀錄，掛在房子上。

**誰這樣做。**
- Rentvine：房子的欄位含 `propertyID`、`isMultiUnit`、地址、經緯度。單位有 `unitID`、`rent`、`deposit`、`beds`、`fullBaths`。房子帶一個 `portfolio` 物件。屋主在 portfolio 的 `owners` 陣列，欄位是 `name`、`email`、`isActive`、`contactID`。持分在 portfolio 的 `contacts`，欄位是 `percentOwned`、`percentDistributed`。見 [Rentvine API 文件](https://docs.rentvine.com)【高】。
- Buildium：建立出租房子時，`rental_owner_ids` 是「已存在的屋主 ID」，`property_manager_id` 是員工 ID。房子內單位上限 100 個。見 [RentalPropertyPostMessage](https://www.rubydoc.info/gems/buildium-ruby/Buildium/RentalPropertyPostMessage)（官方 API 的第三方套件文件）【中】。Buildium 允許多位屋主並設持分，持分合計要 100%。見[搜尋摘要](https://help.buildium.com/hc/s/article/Ownership-percentages-for-properties-with-multiple-owners)【中】。
- Hostaway：管理者把每位屋主建成受限使用者，再指派他擁有的房源。見 [Hostaway 屋主入口](https://www.hostaway.com/features/owner-portal/)【高】。
- Guesty：屋主入口與管理者的帳號同步，資料取自管理者的帳號。支援單一屋主、共同持有、分割持有。見 [Guesty 屋主入口](https://www.guesty.com/guestypedia/owners-portal)【高】。
- Re-Leased：屋主入口顯示每個房子的收支摘要、租約概況、維修與巡檢任務，以及帳單。說明只提「the property manager」單數。見 [Re-Leased landlord portal](https://help.re-leased.com/en/articles/14432415-landlord-portal)【高】。

**套到我們這裡的動作。** 這一類產品的世界裡一個房子只有一個管理方，所以不需要回答「兩個管理方看同一個房子」。rent-poc 的物件已在全域登錄，比這些產品多一層。這類證據只能說明「營運資料放在管理方的範圍內」是常態。

**代價。** 它們的模型在屋主換公司時沒有可借鏡的做法，因為換公司等於換軟體。

### 1.2 屋主帳號對接多家管理公司

**做法。** 每家管理公司有自己的帳號與資料。屋主的登入身分只有一個，連到每家公司。

**誰這樣做。**
- Arthur Online（英國）：每家代理公司是一個 Arthur 帳號。屋主已經與另一家代理合作時，新代理邀請屋主。兩家只要用屋主的同一個 email，Arthur 就把兩個帳號連到屋主的同一個 app。見 [Arthur 支援文章](https://support.arthuronline.co.uk/support/solutions/articles/202000052410)【高】。另外，屋主有多個持有名義時，每個名義是一個帳號。同一 email 可連結，不同 email 要分別登入。見 [Arthur 多持有名義](https://support.arthuronline.co.uk/support/solutions/articles/202000052188-for-agents-who-handle-owners-that-have-properties-under-different-ownerships-under-management)【高】。
- WealthPark（日本）：屋主用一個帳號看多家管理公司的物件。物件清單以管理公司的 logo 區分。收支表依管理公司分開出。對話與確認清單只給該公司。官方原文：「収支表は管理会社ごとに出力されます」「各やりとりの内容は、それぞれの管理会社にのみ公開されます」。見 [WealthPark 複數管理公司](https://owner-app.wealth-park.com/help/chapter1/multiple-pm/)【高】。同一家管理公司內的多個名義另有「マスターアカウント」。見 [master-account](https://owner-app.wealth-park.com/help/chapter1/master-account/)【高】。

**套到我們這裡的動作。** 這兩家都把「屋主是同一個人」當連結點，不把房子的資料合併。對應 rent-poc：屋主組織是連結點，物件與租賃單位是全域登錄，各管理公司的營運資料各存。屋主入口跨公司時，每筆資料標示來自哪家公司。

**代價。** 屋主看到的是多份各自的紀錄，不是一份合併的紀錄。兩家公司對設備清單的描述不同時，沒有機制調解。WealthPark 與 Arthur 的文件都沒有提這個情況。

### 1.3 全平台唯一的識別碼加各方資料

**做法。** 平台或國家發一個唯一識別碼給房子或地塊。各來源、各方把自己的紀錄掛在這個識別碼上。

**誰這樣做。**
- RESO UPI（美加）：RESO 把 UPI 寫成讓資料使用者能「把紀錄對到同一個房子並附加資訊」的標準。第 2.0 版用 URN 格式，編碼含國家、州、郡、地塊號、類型。見 [RESO UPI](https://www.reso.org/universal-property-identifier/) 與 [IANA 登錄](https://www.iana.org/assignments/urn-formal/reso)【中，後者只讀搜尋摘要】。官方原文把名稱從 Property 改為 Parcel，理由是更準確地描述「地塊識別碼與房屋識別碼」的差別【高】。
- RESO 資料字典 1.7：Property 資源有 613 個欄位，含 `ListingKey`，定義是「這筆紀錄在直接來源的唯一識別碼」。也就是 MLS 說的 Property 其實是刊登紀錄，不是實體房子。見 [DD 1.7 Property](https://dd.reso.org/DD1.7/Property/)【高】。
- RESO `UniversalPropertySubId`：定義是「美加所有房地產子集或份額的唯一識別碼」，涵蓋合作社、社區公寓與出租單位。完整地塊用 `UniversalPropertyId`。見 [UniversalPropertySubId](https://dd.reso.org/DD1.7/Property/UniversalPropertySubId/)【高】。
- 英國 UPRN：英國的每個可定址位置一個號碼。由 Ordnance Survey 與地方議會配發，GeoPlace 管理。地方政府協會（LGA）說它在房子的整個生命週期保持不變，從規劃許可到拆除。見 [Wikipedia UPRN](https://en.wikipedia.org/wiki/Unique_Property_Reference_Number)【中】。LGA 頁面抓取 403，原文未讀到。
- Zillow：一個房子一個頁面。屋主認領後能改臥室數、衛浴數、坪數、地塊大小、建造年份。Zestimate 用「公共紀錄與使用者提交的資料」。見 [Zillow 新聞稿 2015-02-27](https://zillow.mediaroom.com/2015-02-27-Homeowners-Can-Now-Change-Their-Home-Facts-Watch-Zestimate-Update-Immediately)【高】。Zillow 的 zpid 與認領流程的官方說明頁抓取 403，只有新聞稿原文。

**套到我們這裡的動作。** ADR-0013 的物件加租賃單位等於 UPI 加 SubId 的做法。`UniversalPropertySubId` 明寫涵蓋「出租單位」，這是租賃單位屬於全域層的直接旁證。Zillow 說明「房子的事實」可以由屋主改、與公共紀錄並存。

**代價。** 這些標準只定識別碼與欄位名，沒有定「多個組織各自的內部資料」放哪。Zillow 沒有多組織管理公司的情境。

### 1.4 主資料管理的通用說法

主資料管理的目標是一份一致的主資料。實務上，各使用者需要的版本不同時，「方案要容許多個版本，並提供透明的調解方式」。若差異不是真需要，就改流程。共用主資料可以保留完整性，同時給各使用者適合的檢視。見 [Wikipedia 主資料管理](https://en.wikipedia.org/wiki/Master_data_management)【中】。

**套到我們這裡的動作。** 這支持「全域一筆加各組織的檢視」。它也提醒一點：先確認各組織的欄位差異是否真的需要。自訂名稱、預設租金、備註確實是各組織自己的。設備清單與格局是否真需要多版本，目前沒有證據。

## 2. 子題二：委任關係放在哪

**做法。** 授權是獨立於房子的紀錄，可撤銷，有等級。

**誰這樣做。**
- Airbnb co-host：房源屬於屋主（host）。co-host 是屋主授權的人，有三個等級：完整權限、日曆與訊息、僅日曆。完整權限的 co-host 能管理刊登、價格與細節，也能加入或移除其他 co-host。只有房源屋主能設定 co-host 的分潤。co-host 看不到屋主或其他 co-host 的收款方式與稅務資料。屋主能隨時移除 co-host。co-host 也能自己退出。屋主要為所有 co-host 負責，包含完整權限 co-host 加入的人。見 [Airbnb co-host 說明](https://www.airbnb.com/help/article/1534)【高】。
- Hostaway：屋主的權限是管理者設定的。管理者決定每位屋主看完整財務或只看日曆。所有模組預設關閉，要逐項開啟。見 [Hostaway 屋主入口](https://www.hostaway.com/features/owner-portal/)【高】。
- Guesty：管理者選擇屋主能看到哪些資訊，並依屋主客製。見 [Guesty 屋主入口](https://www.guesty.com/guestypedia/owners-portal)【高】。
- Hemlane：邀請使用者時設定「Permissions」，決定能進哪些區塊，並選擇能看哪些房子。受邀者已有 Hemlane 帳號時，登入後在自己的儀表板按接受。見 [Hemlane 新增使用者](https://support.hemlane.com/hc/en-us/articles/115007523127-How-do-I-add-a-new-user-manager-owner-agent)【中，頁面 403，內容來自搜尋摘要】。
- Buildium：房子上有 `rental_owner_ids` 與 `property_manager_id` 兩個欄位。管理關係是房子上的欄位，沒有獨立的「管理合約」實體【中】。
- Rentvine：房子透過 portfolio 連到屋主。portfolio 是帳號內的分組，不是合約【高】。

**多個管理關係並存或先後。** 單一管理方軟體沒有這個情境。Airbnb 允許多位 co-host 同時存在於一個房源。Arthur 與 WealthPark 允許一個屋主同時有多家公司，但每家管不同的房子，沒有「同一個房子兩家同時管」的說明【高】。

**套到我們這裡的動作。** 委任是獨立的授權紀錄，這點有 Airbnb 與 Hemlane 的證據。rent-poc 已有這個實體：委託管理案件，附件是委託標的清單，逐列記錄租賃單位與委託範圍（PRD P0-11）。ADR-0013 決議 10 另外保證同一租賃單位同一時間只有一筆有效的主要出租權源。

**代價。** 查到的「獨立的管理合約實體」只有 Airbnb 的授權（授權，不是合約）。沒有找到一家把「管理合約」建成含期間、範圍、報酬的實體。這部分 rent-poc 走在前面，沒有可參照的資料模型。

## 3. 子題三：欄位怎麼分

**做法。** 房子的事實與管理方的內部資料分開。屋主看到的欄位由管理方或授權設定決定。

| 欄位 | 房子的事實 | 管理方內部 | 屋主看得到 | 出處 |
|---|---|---|---|---|
| 地址、經緯度 | 是 | 否 | 是 | Rentvine【高】 |
| 臥室、衛浴、坪數 | 是（Rentvine 把它放在單位上） | 否 | 是 | Rentvine【高】、Zillow【高】 |
| 租金、押金 | 單位上的欄位 | 管理方設定 | 依設定 | Rentvine【高】 |
| 收支、帳單 | 否 | 是 | 是，限屋主自己的房子 | Re-Leased【高】、Hostaway【高】 |
| 租約概況、維修、巡檢任務 | 否 | 是 | 是 | Re-Leased【高】 |
| 清潔與巡檢照片 | 否 | 是 | 是 | Guesty【高】 |
| 內部備註、佣金、廠商 | 否 | 是 | 查不到說明 | 未查證 |
| 收款方式、稅務 | 否 | 是 | co-host 看不到屋主的 | Airbnb【高】 |

**套到我們這裡的動作。** 屋主看得到的欄位建議用固定清單，不逐筆設定。依 PRD P0-09 的權限表，代管案件的屋主已能讀合約與帳務、讀報表、確認點交。「屋主可讀營運資料的哪些欄位」尚未定義，這是本次要補的缺口。

**代價。** 固定清單簡單，但每家公司對「內部備註」的用法不同，可能有人把給屋主看的話寫進內部備註。

## 4. 子題四：誰能改

**做法。** 房子的事實誰能改，各家不同。

- Zillow：屋主認領後改房屋事實。屋主是權威【高】。
- Airbnb：完整權限的 co-host 能改刊登的細節與價格。收款資料只有屋主能設定【高】。
- Hostaway：屋主是受限使用者，能看帳單與自己的住宿。可以封鎖自己的日期。看不到改房源設定的說明【高】。
- Guesty：管理者決定「屋主能做或不能做什麼」【高】。
- Buildium：屋主入口含核准功能。核准的對象是管理者提交的項目，不是改房子資料【中】。

設備清單與單位切分由誰維護，查不到任何一家的說明。單位切分在這些產品都由管理方在帳號內設定。

**套到我們這裡的動作。** ADR-0013 決議 5、6 已規定租賃單位由平台發行 ID 與後綴，出租人決定怎麼切。屋主若沒有出租人身分，不能改切分。營運資料（設備清單）由各組織維護，屋主透過請求要求修改。這與 DoorLoop 的「屋主入口送請求給管理公司」一致（見 q30 筆記 A1）。

**代價。** 屋主覺得設備清單錯了，只能請業者改，不能自己改。

## 5. 子題五：換業者時資料怎麼走

**查到的。**
- Arthur 與 WealthPark 的文件說明如何「加入第二家公司」。沒有說明「換公司」。新公司邀請屋主，用同一個 email 或登入 ID 連結帳號【高】。
- 舊公司的資料留在舊公司的帳號。WealthPark 明寫每家的收支表與對話只給該公司【高】。
- AppFolio 的官方移轉流程查不到。第三方只說屋主入口能匯出報表為 Excel 或 CSV【低，第三方公司指南】。
- 一個英國學生住宅產品（PAD Group）的房源移轉工具提供「Move」與「Copy」兩個選項，建議用 Move，使房源只在一個帳號。見 [PAD Group 房源移轉](https://support.pad-group.com/portal/en/kb/articles/how-to-move-a-property-from-landlord-s-account-to-another-using-the-property-transfer-tool)【中，搜尋摘要，與管理公司軟體無關】。

**結論。** 歷史帳務與文件「留在舊業者、屋主可要」是查得到的做法。官方的匯出或移轉流程只有 PAD 一家，且不是同類產品。

**套到我們這裡的動作。** rent-poc 的移交包已做完（ADR-0024）：後繼案件承接同一個租賃單位 ID，快照存兩側，舊受託人保留唯讀副本。PRD P0-22 的六類內容含屋況，屋況含點交紀錄、現況確認附件、設備附件。所以設備資料的搬運路徑已經有了：走移交包，不走共用欄位。

**代價。** 新業者看到的設備清單是移交當下的快照。移交後兩邊各自演變。

## 6. 子題六：屋主沒有帳號時

**做法。** 管理公司先建屋主的聯絡人紀錄，再發邀請。

- DoorLoop：在 People > Owners 建屋主紀錄，開啟邀請，屋主設密碼。邀請信只顯示公司名稱。見 [DoorLoop](https://support.doorloop.com/en/articles/8317361-invite-an-owner-to-the-owner-portal)【高，q30 筆記已讀】。
- Hostaway：屋主登入的帳號由管理者建立，Hostaway 本身不替屋主建【中，搜尋摘要】。
- Guesty：每個 email 只能對應一位屋主的入口【中，搜尋摘要】。
- Hemlane：屋主可為自己的帳號邀請管理者【中】。

**屋主自己有帳號、能自己登錄房子的平台。**
- Zillow：屋主用認領流程進入。房子頁面已存在，屋主認領的是既有頁面【高】。
- Airbnb：屋主自己建房源，再邀請 co-host【高】。
- Arthur：屋主有自己的 app。多家代理用同一個 email 連到同一個 app【高】。
- WealthPark：帳號由管理公司發放，但屋主的登入 ID 可跨公司共用【高】。

**套到我們這裡的動作。** rent-poc 的屋主有組織。屋主沒有組織時，由管理公司邀請建立。屋主組織建立後，所有受託人用同一個屋主組織，與 Arthur、WealthPark 的做法相同。

**代價。** 屋主沒有 email 或不上線時，要有代理人（管理公司）登錄的退路。

## 8. 對產品負責人直覺的檢驗

直覺：物件只有一筆。屋主與代管業者看到的差別來自委任，委任與物件分開。

| 部分 | 證據 | 判定 |
|---|---|---|
| 物件只有一筆 | UPI、UPRN、Zillow 都只有一個房子。ADR-0013 已是如此 | 支持，且已實作 |
| 租賃單位也全域唯一 | RESO `UniversalPropertySubId` 涵蓋出租單位 | 支持 |
| 委任與物件分開 | Airbnb co-host 授權獨立於房源。Hemlane 邀請獨立於房子。rent-poc 已有委託管理案件 | 支持 |
| 看到的資料由委任決定 | Airbnb 三級、Hostaway 與 Guesty 依屋主設定 | 支持 |
| 委任期間受託人讀寫物件的共用資料 | Airbnb 完整權限 co-host 能改刊登。其他管理軟體由管理方自己維護房子紀錄 | 部分支持。這些情境的房子屬於授權方，或屬於管理方，兩者不並存 |
| 委任結束就失去權限 | Airbnb 屋主移除 co-host 即失權 | 支持權限結束 |
| 內部資料掛在委任或組織上 | 管理軟體把內部資料放在管理方帳號內 | 支持掛在組織上。掛在委任上查不到 |
| 營運資料也合成一筆 | 查不到任何產品讓兩個互不隸屬的管理公司共同維護同一份房子資料 | 反對 |

反對的理由還有三條，都是 rent-poc 自己的條件，不是業界證據【低】：

1. 受託人的帳務、維修、收款紀錄有保存義務與稽核需要。委任結束時失去讀取權限，會與 ADR-0024 決議 6 的「舊受託人保留唯讀副本」衝突。
2. 包租不是委任。包租業者以自己的名義出租，出租權源鏈放在出租人的組織（ADR-0026 決議 4）。方案丙的「委任決定權限」套不到包租。
3. 兩個組織同時登錄同一物件時（屋主自己登錄過，之後委託代管），合成一筆需要決定誰的設備清單算數。業界沒有範例。

## 9. 套用到 rent-poc 的建議

現況對照：物件與租賃單位在全域登錄（ADR-0013）。換經理人時新組織建立自己的營運資料，指向同一個租賃單位 ID（ADR-0013 決議 9）。移交包含屋況與設備附件，快照存兩側（ADR-0024）。產權模組、撞號送審、分租、封存、移交包都已完成。

改動量分三級：
- 一級：只改文件與用詞。
- 二級：加欄位與讀取權限，不動資料表歸屬。
- 三級：改資料表歸屬，影響 RLS、遷移與已完成的模組。

### 方案甲：維持現況

| 項目 | 內容 |
|---|---|
| 資料放哪 | 物件與租賃單位全域唯一。營運資料每個組織一份 |
| 誰看得到 | 屋主看不到業者的營運資料。屋主讀合約與帳務經案件成員（P0-09） |
| 誰能改 | 各組織改自己的營運資料 |
| 換業者 | 新組織建新營運資料。設備經移交包的屋況類帶過去 |
| 改動量 | 一級（把「物件」一詞改為指全域那層，營運資料另立名稱） |
| 代價 | 屋主看不到業者端的設備清單。同一房子有多份描述，彼此可能不一致 |

### 方案乙：房子的事實搬到全域層

| 項目 | 內容 |
|---|---|
| 資料放哪 | 格局、設備清單、照片、單位切分放全域層。各組織只留自訂名稱、備註、預設租金 |
| 誰看得到 | 凡與該物件有關係的組織都讀全域事實 |
| 誰能改 | 需要新規則。屋主、現任受託人、包租業者誰能改？衝突時誰算數？ |
| 換業者 | 設備與照片留在物件，不必搬 |
| 改動量 | 三級。要新增全域表、改 RLS、遷移既有設備資料，移交包的屋況類要改寫 |
| 代價 | 沒有業界範例。需要調解多人編輯。撞號送審期間誰能改全域事實，要新增規則。Phase 1 剩約 44 張票，難以吸收 |

### 方案丙：產品負責人的直覺

| 項目 | 內容 |
|---|---|
| 資料放哪 | 物件一筆。營運資料併入物件，內部資料掛在委任或組織上 |
| 誰看得到 | 委任期間受託人讀寫共用資料。屋主一直能讀。委任結束受託人失權 |
| 誰能改 | 委任期間屋主與受託人都能改共用資料 |
| 換業者 | 委任結束，舊業者失去讀取。新業者的委任開始就能讀 |
| 改動量 | 三級，比乙更大。`org.properties` 要拆開，所有以 `org_id` 做的 RLS 要改成以關係做 |
| 代價 | 與移交包的舊受託人唯讀副本衝突。套不到包租。業界沒有兩個互不隸屬的管理公司共同維護同一份資料的範例 |

### 方案丁：方案甲加委任當獨立關係，屋主經關係讀指定欄位（推薦）

| 項目 | 內容 |
|---|---|
| 資料放哪 | 同方案甲。委任沿用委託管理案件與委託標的清單，不新增表 |
| 誰看得到 | 屋主經案件成員讀營運資料的固定欄位清單：租賃單位名稱、設備清單、備註中標示「對屋主可見」的部分。內部備註、佣金、廠商不給。包租的屋主只讀租期與狀態（沿用 P0-09 表格） |
| 誰能改 | 營運資料由各組織改。屋主提出修改請求，不直接改 |
| 換業者 | 設備與屋況經移交包複製到後繼案件。內部備註不帶 |
| 改動量 | 二級。加「對屋主可見」的欄位標記，加一條讀取政策，屋主入口顯示對應欄位 |
| 代價 | 多份描述仍可能不一致。屋主看到的是業者填的版本 |

### 推薦：方案丁

理由：

1. 證據。Arthur、WealthPark、Hostaway、Guesty、Re-Leased 都把資料放在管理方範圍，屋主經授權讀指定欄位【高】。沒有範例支持方案乙與丙的共同編輯。
2. 授權獨立於房子有 Airbnb 與 Hemlane 的範例【高、中】。rent-poc 的委託管理案件已經是這個實體，所以不必新建。
3. 已完成的模組不動。產權模組、撞號、分租、封存、移交包都不用改。
4. 符合隔離。RLS 仍以組織為界，新增的只是「屋主經案件關係讀指定欄位」。
5. 保留升級路徑。若日後發現兩個組織常對設備清單看法不同，且產品負責人要求單一版本，再升級到方案乙。這不是推翻方案丁，是把設備清單那幾欄搬到全域層。

升級到方案乙的觸發條件建議為：實際營運中，同一物件的設備清單在兩個組織間不一致，造成客訴或糾紛，且次數達到你定的門檻。
