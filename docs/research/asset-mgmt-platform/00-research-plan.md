# 調研計劃：台灣不動產資產管理平台

日期：2026-10-29
狀態：2026-10-29 使用者確認，執行中
目的：完成一份可行的商業計劃提案（BRD）與產品需求（PRD），並用 ELI5 說明商模與系統架構。

## 一、題目範圍

### 使用者給的定位

- 產業：台灣不動產。
- B 端場景：資產管理、移交、信託、合約管理。
- C 端場景：房屋租賃與買賣媒合（類似 591）。
- 參考商模：第一銀行「不動產買賣價金信託」、僑馥建經「不動產買賣價金信託履約保證」。

### 已讀取的參考資料

第一銀行頁面：銀行信託部擔任受託人。買賣雙方簽買賣契約後，再與銀行簽信託契約。買方把價金存入信託專戶。雙方共同指示後，銀行才付稅費、仲介費、賣方貸款。過戶完成後，銀行把信託財產交付賣方。保障機制是專戶獨立、不可強制執行、雙方共同指示。

僑馥建經頁面：流程分七段，簽約前、簽約後、用印、完稅、過戶、點交、結案。角色有經紀業及地政士、買賣雙方、僑馥。建經公司負責通知、審閱、把關各段的款項與文件。

兩者的共同點：平台本身不持有價金，錢在銀行信託專戶。平台的價值在流程把關與多方協作。

### 本計劃的假設

1. 「資產管理」指不動產的物業與租賃資產管理。不含金融資產管理公司（AMC）的不良債權業務。
2. 平台不自己收受價金或租金，不自己擔任受託人。平台串接銀行信託專戶或建經公司。
3. 既有 rent-poc 的電子簽約、合約三層文件、設備附件，是這個平台的合約管理模組起點。

假設錯誤時，請在確認時指出。

## 三、調研子題（7 位 Sonnet 調研員，平行執行）

### R1：台灣 B 端服務盤點

- 範圍：履約保證、價金信託、物業管理、包租代管、資產管理軟體。
- 對象：第一銀行、僑馥建經、東亞建經、群義建經、永慶與信義的履保、JGB Property、包租代管業者、社會住宅包租代管。
- 要回答：各家的服務流程、收費、角色分工、法律關係、系統有哪些功能。

### R2：台灣 C 端媒合平台

- 範圍：租賃與買賣媒合。
- 對象：591、樂屋網、好房網、信義與永慶線上平台、租屋平台新創。
- 要回答：商模（刊登費、會員費、成交佣金、加值服務）、流量與定價、廣告責任與法規限制、租客與房東的痛點。

### R3：國外標竿

- 範圍：PropTech 資產管理、租賃媒合、數位 escrow。
- 對象：Yardi、AppFolio、Buildium、RealPage、Entrata、Zillow、Rightmove、Qualia、Snapdocs、Endpoint、PropertyGuru、日本 GA technologies、韓國 Zigbang。
- 要回答：商模、收費、模組切分、系統架構公開資訊、失敗案例（如 Zillow Offers）。

### R4：法規與風險

- 範圍：台灣法規。
- 要查：信託法、信託業法、不動產經紀業管理條例、租賃住宅市場發展及管理條例、個人資料保護法、洗錢防制法對地政士與經紀業的義務、電子簽章法 2024 修法、電子支付機構管理條例、第三方支付代收代付限制、消費者保護法定型化契約、公平交易法廣告規範。
- 要回答：平台哪些事不能自己做、哪些事要牌照、哪些事要合作方、各法規的罰則。
- 每條結論必須引用條號與主管機關來源。

### R5：移交與資產管理的領域流程

- 範圍：點交、交屋、物業移交、信託財產移交、管理費與修繕、設備資產追蹤。
- 要回答：每段流程的角色、文件、款項、常見糾紛、內政部範本與現況確認書的要求。

### R6：系統架構參考

- 範圍：多租戶 SaaS、金流與信託專戶整合、電子簽章、eKYC、文件與稽核軌跡、帳務分錄。
- 要查：台灣銀行虛擬帳號與開放銀行 API、第三方支付整合、事件溯源帳本、資料保護與稽核設計。
- 要回答：可行的參考架構、各模組的邊界、既有 rent-poc 可沿用的部分。

### R7：台灣不動產物件的紀錄結構與唯一性

- 範圍：政府如何唯一識別一筆不動產，平台如何確保同一物件只登錄一次。
- 要查：地號、建號、建物門牌、地籍圖資網路便民服務系統（easymap.moi.gov.tw）、土地與建物登記謄本、房屋稅籍編號、實價登錄的識別方式、政府開放資料與 API、地政司的「不動產資料整合」。
- 要回答：哪個識別碼能當物件主鍵、租賃的分割單位（分租套房、雅房）如何對應建號、識別碼的取得流程與成本、查驗所有權的合法方式與個資限制。

## 四、稽核與合成

1. 七位調研員完成後，Opus 稽核員逐篇檢查。檢查項目：來源可追溯、法條條號正確、數字有出處、筆記之間沒有矛盾。
2. 稽核員列出缺口。缺口影響商模判斷時，補派一輪調研。只補一輪。
3. 報告撰寫員合成調研報告。Opus 稽核員再檢查報告一次。
