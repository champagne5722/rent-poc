## 0. 讀法

### 0.1 義務詞與標示

| 詞 | 意思 |
|---|---|
| 必須 | 義務。上線前必須做到 |
| 不得 | 禁止 |
| 得 | 許可。系統允許，但不強制 |
| 建議 | 建議，並附適用條件 |

「應」只出現在合約條文。
數字與法規結論後的【高】【中】【低】沿用調研報告的信心標示。
「待函詢」表示屬於第二輪報告的三個灰區。函詢回覆前，本 PRD 一律採保守設計。
「待使用者拍板」表示 v1 留下的三條爭議需求。本 PRD 先寫 v1 的版本，見 7.1。
「假設」表示產品設定的數字，不是事實。

### 0.2 角色與契約地位

本 PRD 分開寫兩件事：合約上的地位，與平台上的身分。

| 合約類型 | 甲方 | 乙方 | 依據 |
|---|---|---|---|
| 租賃合約 | 出租人：屋主或包租業者 | 承租人 | 內政部住宅租賃契約書範本 |
| 委託管理合約 | 委託人：屋主 | 受託人：代管業者 | 租賃條例 §32 第 1 款 |

| 本 PRD 用詞 | 意思 |
|---|---|
| 屋主 | 租賃單位的登記所有權人，或經其授權使用平台的人 |
| 出租人、承租人 | 租賃合約的甲方與乙方 |
| 委託人、受託人 | 委託管理合約的甲方與乙方 |
| 經理人 | 代管業者、包租業者、經紀業者的角色統稱。不是法定名詞 |
| 執業主體 | 持有許可或登記的公司或商號，是合約當事人 |
| 執業人員 | 持有證書的自然人，是簽章人，受僱於執業主體 |
| 平台營運者 | 平台的審核與客服人員 |
| 系統 | 平台提供的軟體 |

經理人在介面上必須顯示法定稱謂，對照如下：

| 業別 | 執業主體的法定稱謂 | 執業人員的法定稱謂 |
|---|---|---|
| 代管 | 租賃住宅代管業者 | 租賃住宅管理人員 |
| 包租 | 租賃住宅包租業者 | 租賃住宅管理人員 |
| 經紀 | 不動產經紀業者 | 不動產經紀人、不動產經紀營業員 |

同一位屋主在不同合約有不同地位。
委託代管時，屋主是委託管理合約的委託人，也是租賃合約的出租人。
交給包租業時，屋主是出租人，包租業者是承租人。包租業者轉租時，包租業者是出租人。
經理人得同時是某份合約的甲方或乙方。

### 0.3 術語變更

本 PRD 使用 BRD 第 13 節的提案詞。下表的變更必須在審閱通過後寫入 `GLOSSARY.md`。

| 詞 | 現行定義 | 變更 |
|---|---|---|
| 房東 | 系統唯一操作者，即合約甲方 | 包租案件的出租人是包租業者，房東不再等於甲方。需求文字改寫「屋主」或「出租人」 |
| 租客 | 承租人，不進系統 | 改寫「承租人」，並登入承租人端查閱 |
| 屋主 | 列在「房東」的 _Avoid_ | 新增條目，定義見 0.2 |
| 甲方、乙方 | 列在 _Avoid_，合約內文除外 | 新增條目，依合約類型定義 |
| 合約 | 一份租賃合約 | 擴大為租賃合約與委託管理合約。新增「文件類型」 |
| 物件 | 房東持有的可出租單位 | 對應一個租賃單位。需求文字一律寫「租賃單位」 |
| 案件 | 列在「簽署任務」的 _Avoid_ | 新增條目。案件是跨方流程，簽署任務是點點簽的一次送簽 |
| 稽核紀錄 | 列在「合約歷程」的 _Avoid_ | 新增條目。合約歷程維持活動性質，稽核紀錄承擔防竄改 |
| 應收期別、修繕紀錄、資產總覽 | 無 | 本 PRD 新增，定義見各需求 |

GLOSSARY 規定識別字與介面標題用「合約」。
本 PRD 把系統文件類型寫成「委託管理合約」與「租賃合約」。
引用法條時保留法定名稱，例如「委託管理契約書」。

## 1. 問題陳述

屋主要管多間房子，必須面對代管、仲介、地政、銀行四種服務商。
多數屋主用試算表或 LINE 串起租約、押金、收租與修繕。
經理人要向屋主證明自己持照、守規矩，證照目前靠紙本。
承租人簽約前無法確認出租人有權出租。

| 主張 | 證據 | 信心 |
|---|---|---|
| 3 戶以上非自住屋主約 41,188 人，5 戶以上 8,388 人 | BRD 第 4 節 | 中 |
| 調查範圍內沒有一家把六塊服務放進同一個屋主入口 | 第二輪報告第 4 章 | 中 |
| 管理業務含收租與押金管理，無照罰 4 萬至 20 萬元 | 租賃條例 §36 | 高 |
| 代管與包租的簽章義務不同，第 1 款不適用包租，第 2、3 款不適用代管 | 租賃條例 §32 | 高 |
| resim 有證書與任職查詢，皆附驗證碼 | 第二輪報告 6.2 | 高 |
| 未查到主管機關對平台為無照者提供撮合的裁罰或函釋 | 第二輪報告 6.5 | 低 |
| 租屋詐騙 2025 年 1 至 9 月損失逾 3,000 萬元，受害者轉向房東 | 第一輪報告，刑事局說明 | 中 |
| 屋主需求只有供給端訊號，沒有屋主調查 | BRD 第 2 節 | 高 |

問題本身有法規與報導支持。屋主付費意願沒有證據，這是 G1 要驗證的事。

## 2. 目標

### 使用者目標

| 編號 | 目標 | 量測 |
|---|---|---|
| U1 | 屋主在一頁看到所有租賃單位的租約、押金、收租、修繕狀態 | 資產總覽週活躍率，見 L9 |

| U5 | 押金每筆變動都能追到證據 | 已結案案件中，每筆扣抵附證據的比例 |

## 3. 非目標

| 編號 | 非目標 | 理由 |
|---|---|---|
| N1 | 不持有款項。平台不收、不保管、不撥付租金與押金，也不提供平台名下的收款帳戶 | 代收轉付落入電支條例文義，自行收款再信託落入信託業法 §33。第一輪報告已確立 |
| N2 | 不居間。平台不帶看、不議價、不挑選承租人、不依成交計酬 | 經紀條例 §4、§32【高】。平台媒合是否構成仲介屬灰區一，待函詢 |

| N4 | 不做買賣流程層 | 屬 Phase 2，關卡 G1 放行後才開始 |
| N5 | 不做信託帳戶。不串接信託專戶，不提供查帳連結 | 屬 Phase 2。經理人或平台向銀行查帳沒有法源【高】 |
| N6 | 不做自有房源上架 | 屬 Phase 2，等灰區一函詢結果 |
| N7 | 不做全資產清冊與繼承協調 | 屬 Phase 3 |
| N8 | 不以程式自動查詢 resim | resim 附圖形驗證碼【高】。自動化必須先取得內政部地政司核准 |
| N9 | 不保證經理人合法 | 標章只表示證書資料已核對，避免形成不當擔保 |
| N10 | 不做租賃所得申報 | BRD R12。系統不強制屋主申報 |

| ADR-0007 | 平台側稽核紀錄屬新範圍，必須寫新 ADR |
| ADR-0008 | 委託管理合約與現況確認附件改變文件組成 |

### 5.2 P0：沒有就不能上線

P0 共 24 條，分六組。

| 組別 | 需求 |
|---|---|
| 身分與驗證 | P0-01 至 P0-05 |
| 物件 | P0-06 至 P0-08 |
| 案件與合約 | P0-09 至 P0-12 |
| 帳務 | P0-13 至 P0-15 |
| 租期中與退租 | P0-16 至 P0-18 |
| 屋主、承租人、移交、橫向 | P0-19 至 P0-24 |

#### P0-01 三種身分與合約地位

系統的帳號一律是自然人。一個帳號得有多種身分。
甲方與乙方依合約類型決定，對照見 0.2。
甲方與乙方沒有執業證照要求，身分驗證用一般 KYC 加簽署人驗證。
經理人是角色統稱。合約文件、標章、承租人端不得以「經理人」作為稱謂。
上述位置必須顯示 0.2 的法定稱謂。系統內部選單得使用「經理人」。
執業主體兼營代管與包租時，系統依案件的業務類型顯示稱謂。
自然人沒有自己的公司時，只能以執業人員身分掛在執業主體下。
執業主體是合約甲方或乙方時，合約當事人是執業主體。
執業主體的當事人簽署人由執業主體指派，資格待法務確認（Q12）。
地政士不屬經理人。Phase 1 不開放地政士角色。

| AC | Given | When | Then |
|---|---|---|---|
| 1 | 屋主自管一個租賃單位 | 建立租賃合約 | 甲方為屋主，介面顯示「出租人」 |
| 2 | 包租業者轉租一個租賃單位 | 建立租賃合約 | 甲方為該執業主體，介面顯示「租賃住宅包租業者」 |
| 3 | 屋主委託代管 | 建立委託管理合約 | 甲方為委託人屋主，乙方為受託人代管業者 |
| 4 | 自然人帳號沒有所屬執業主體 | 申請經理人功能 | 系統要求先綁定一個執業主體 |
| 5 | 執業主體兼營代管與包租 | 開啟一個包租案件 | 介面顯示「租賃住宅包租業者」 |
| 6 | 任何合約 PDF | 系統產出文件 | 文件內不出現「經理人」字樣 |

#### P0-02 組織與資料隔離

組織是資料隔離單位，分兩類：屋主組織、執業主體組織。
一個執業主體對應一個組織。一個帳號得屬於多個組織。
執業主體組織的驗證狀態不是「已驗證」時，不得建立代管或包租案件。
所有組織資料表必須以 PostgreSQL RLS 隔離，並設定 `FORCE ROW LEVEL SECURITY`。
應用程式連線角色不得是資料表擁有者，也不得有 `BYPASSRLS`。
系統不得把一個組織的非公開租金資料，用在其他組織的統計。
平台營運者只得透過審核佇列或支援工單存取組織資料。
每次營運者存取都必須寫入稽核紀錄。

| AC | Given | When | Then |
|---|---|---|---|
| 1 | A 組織成員已登入 | 以 B 組織的資料 ID 直接呼叫 API | 回應與「資料不存在」相同 |
| 2 | 連線沒有設定組織變數 | 執行查詢 | 回傳 0 筆 |
| 3 | 連線池重用同一條連線 | 前一請求屬 A，後一請求屬 B | B 讀不到 A 的資料。此案例必須有自動化測試 |
| 4 | 執業主體組織為「待驗證」 | 建立代管案件 | 系統擋下，顯示驗證狀態 |
| 5 | 第一家外部組織上線前 | 執行跨組織滲透測試 | 高風險發現為 0 件 |
| 6 | 成員已被移出組織 | 該成員送出下一個請求 | 系統拒絕存取，並寫入稽核紀錄 |

技術考量：組織識別建議以交易層級變數設定，避免連線池外洩 session 狀態。
遷移前建議先抽出資料存取層。遷移工作量待工程估算（Q13）。

#### P0-03 執業主體驗證

執業主體的欄位如下：

| 欄位 | 說明 |
|---|---|
| 統編 | 公司或商號統一編號 |
| 業別 | 代管、包租、經紀，得複選 |
| 許可或登記證字號 | 依業別分列 |
| 營業項目代碼 | 代管 H706011，包租 H706021，經紀 H704031 |
| 登記狀態 | 取自商工登記 API |
| 驗證狀態 | 已驗證、待驗證、已失效 |
| 最近驗證日、驗證者、驗證結果 | 每次驗證都保留 |

驗證流程如下：

1. 執業主體填寫統編、業別與許可或登記證字號。
2. 系統以商工登記 API 查公司或商號的存在、狀態與營業項目。
3. 平台營運者在 resim 業者查詢核對許可或登記證字號。
4. 兩項都一致時，系統把驗證狀態改為「已驗證」。

規則如下：

1. 業別必須有對應的營業項目代碼。H703100 不構成代管業資格【高】。
2. 代管與包租的執業主體必須是公司。個體商號不得登錄為代管或包租業者。
3. 經紀業的執業主體得為公司或商號。
4. 商工 API 只證明公司存在、狀態與營業項目，不能證明許可或登記證。
5. 商工 API 須填使用告知書與 IP 白名單，並有連線與每日次數管制【高】。
6. API 失敗時，系統維持原狀態並送人工佇列，不得自動改為「已驗證」。
7. 登記狀態不是核准設立時，系統把驗證狀態改為「已失效」。
8. 系統建議每月以商工 API 重查一次登記狀態。頻率是假設。
9. 「已失效」的執業主體不得建立新案件，也不得送簽新文件。
10. 執業主體改為「已失效」時，系統必須通知其案件的屋主，並提示移交（P0-22）。

| AC | Given | When | Then |
|---|---|---|---|
| 1 | 統編查得公司，營業項目含 H706011 | 營運者核對許可字號一致 | 狀態改為「已驗證」，記錄驗證者、時間、結果 |
| 2 | 業別選代管，營業項目只有 H703100 | 系統查詢商工 API | 系統拒絕該業別，顯示缺少的代碼 |
| 3 | 統編屬於商號 | 業別選包租 | 系統拒絕，說明租賃線限公司 |
| 4 | 商工 API 逾時 | 送出驗證 | 狀態維持「待驗證」，進人工佇列 |
| 5 | 已驗證的公司在月度重查顯示停業 | 排程執行 | 狀態改為「已失效」，通知其案件的屋主 |
| 6 | 執業主體為「已失效」 | 成員按送簽 | 系統擋下送簽，顯示失效原因 |

#### P0-04 執業人員驗證與效期

執業人員的欄位如下：

| 欄位 | 說明 |
|---|---|
| 證書種類 | 租賃住宅管理人員、不動產經紀人、不動產經紀營業員 |
| 證號 | 年、字、號三段 |
| 發證日、效期 | 效期依證書種類 |
| 所屬執業主體 | 一筆任職對應一個執業主體 |
| 任職狀態 | 在職、離職 |
| 專任旗標 | 是或否 |
| 同意書 | 經紀人員為他家執行業務時必填，見 P0-05 |
| 驗證狀態 | 已驗證、待驗證、已失效 |

驗證流程如下：

1. 執業人員填寫證書資料，並上傳證書影本。
2. 平台營運者在 resim 的證書查詢與任職查詢核對資料。
3. 資料一致時，營運者記錄驗證結果，系統把狀態改為「已驗證」。
4. 系統在執業人員的頁面顯示標章「證書資料已核對」與驗證日。

規則如下：

1. resim 附圖形驗證碼【高】。系統不得以程式繞過驗證碼。
2. 批次核對管道必須先取得內政部地政司核准，見 P1-07。
3. 標章文字固定為「證書資料已核對」。
4. 標章與介面不得出現「保證合法」「認證」「擔保」等字樣。
5. 三種證書的效期都是 4 年。系統依發證日計算期滿日。
6. 期滿前 6 個月，系統通知執業人員與所屬執業主體換證。
7. 逾期未換證、證書遭廢止或任職異動，狀態改為「已失效」。
8. 「已失效」的執業人員不得被指派到新的簽章欄。
9. 已送簽而未簽的簽章欄，系統通知執業主體撤回後改派。
10. 管理人員異動後，業者須 30 日內造冊報備（§21）。系統在任職結束時提醒執業主體更新。
11. 管理人員證書的正式指定發證單位未查到。營運者核對時以 resim 結果為準。

個資保存規則如下：

1. 系統只保存證書種類、證號、發證日、效期、驗證日、驗證者與結果。
2. 驗證完成後，系統刪除證書影本，或遮罩身分證字號與地址。
3. 保存期限由平台自訂並寫入隱私權政策，由法務確認（Q14）。

| AC | Given | When | Then |
|---|---|---|---|
| 1 | 管理人員上傳證書 | 營運者在 resim 核對一致 | 狀態改為「已驗證」，顯示「證書資料已核對」 |
| 2 | resim 查無該證號 | 營運者判定 | 狀態維持「待驗證」，系統通知執業人員補件 |
| 3 | 證書期滿日在 6 個月後 | 每日排程執行 | 執業人員與執業主體收到換證提醒 |
| 4 | 證書已過期滿日且未換證 | 每日排程執行 | 狀態改為「已失效」，該人員不得被指派簽章 |
| 5 | 驗證完成 | 系統處理影本 | 影本刪除或遮罩，稽核紀錄記下處理方式 |
| 6 | 任何頁面顯示標章 | 載入頁面 | 文字為「證書資料已核對」，不含保證字樣 |
| 7 | 已指派的管理人員改為「已失效」 | 該簽署任務仍在簽署中 | 系統通知執業主體撤回後改派 |

#### P0-05 專任規則分流

租賃住宅管理人員與經紀人員的專任規定不同，系統必須分開檢查。

| 項目 | 租賃住宅管理人員 | 經紀人員 |
|---|---|---|
| 條文 | 租賃條例 §25 | 經紀條例 §16 |
| 規定 | 專任者不得同時受僱於二家以上，無但書 | 應專任一家。經所屬業者同意者，得為他家執行業務 |
| 系統動作 | 同一證號同時掛兩家執業主體：阻擋 | 同一證號掛兩家：提示，並要求上傳所屬業者同意書 |

規則如下：

1. 管理人員已有一筆在職任職時，系統不得建立第二筆在職任職。
2. 阻擋訊息不得揭露第一家執業主體的名稱。
3. 舊任職改為離職後，第二家才得建立任職。
4. 代管或包租的執業主體至少要有一名已驗證的專任管理人員，才得建立案件（§25）。
5. 經紀人員掛第二家時，系統要求上傳所屬經紀業的同意書。
6. 營運者核對同意書後，第二家的任職標示「經所屬業者同意」。
7. 同意書撤回或到期時，第二家的任職改為「已失效」。
8. 每次阻擋與提示都寫入稽核紀錄。

| AC | Given | When | Then |
|---|---|---|---|
| 1 | 管理人員 X 在 A 公司在職 | B 公司新增 X 的任職 | 系統阻擋，訊息為「此證號已有在職紀錄」，不顯示 A |
| 2 | X 在 A 公司的任職改為離職 | B 公司新增 X 的任職 | 系統允許，狀態為「待驗證」 |
| 3 | 經紀人 Y 在 C 經紀業在職 | D 經紀業新增 Y 的任職 | 系統提示，要求上傳 C 的同意書 |
| 4 | Y 的同意書已上傳且核對 | D 指派 Y 簽章 | 系統允許 |
| 5 | 代管公司沒有已驗證的專任管理人員 | 建立代管案件 | 系統擋下，說明 §25 的要求 |
| 6 | 系統阻擋一筆任職 | 阻擋發生 | 稽核紀錄有證號、時間、阻擋原因 |

#### P0-06 產權錨點與租賃單位

產權錨點的唯一鍵是「縣市＋鄉鎮市區＋段小段＋建號（含分號）」。
建號只在地段內唯一，系統不得單用建號比對【高】。
租賃單位掛在產權錨點下。後綴 0000 代表整戶，分租單位以房號為後綴。
每個租賃單位另有系統發的單位 ID。單位 ID 無語意，不隨門牌或錨點變動。
共有部分建號、基地地號、稅籍編號存為輔助資料，不參與唯一鍵。
產權錨點綁產權，不綁人。所有權人變更時，錨點不變。

| AC | Given | When | Then |
|---|---|---|---|
| 1 | 使用者有完整的複合鍵 | 新增產權錨點 | 系統建立錨點，狀態為「已建號」 |
| 2 | 使用者沒有建號 | 只填門牌與座標 | 系統建立「待驗證」錨點，其下的租賃單位得擬約 |
| 3 | 「待驗證」錨點補上建號 | 補上的複合鍵已存在 | 系統把該案送 P0-07 審核，不自動合併 |
| 4 | 整戶單位有生效中的合約 | 使用者在同一錨點新增分租單位 | 系統顯示衝突警告，使用者確認後才建立 |
| 5 | 系統已有物件資料 | 執行資料遷移 | 每個物件成為一個租賃單位，錨點狀態為「待驗證」 |
| 6 | 代管業者有 500 列的 CSV | 批次匯入 | 系統逐列回報成功、失敗與疑似重複 |
| 7 | 錨點的登記所有權人變更 | 使用者更新出租權源 | 錨點與單位 ID 不變 |
| 8 | 租賃單位有任何案件 | 使用者刪除該單位 | 系統不得刪除，只得封存 |

技術考量：資料表建議使用 `property_anchor`、`rental_unit`、`supporting_ids`。
門牌歷史屬 P1-03。P0 的門牌欄位必須能無損遷入 `address_history`。

#### P0-07 重複登錄偵測

偵測分兩層。硬性層以複合鍵做全平台唯一約束。
軟性層比對正規化門牌、座標、樓層、房號。相近者送平台營運者審核。
分租單位沒有官方識別碼，偵測最弱，必須搭配 P0-08 的出租權源驗證。
跨組織撞號時，系統不得向後登錄者揭露先登錄組織的名稱與資料。
同一租賃單位同一時間只能有一筆有效的主要出租權源。

| AC | Given | When | Then |
|---|---|---|---|
| 1 | A 組織已登錄某複合鍵 | B 組織新增相同複合鍵 | 系統顯示「此產權已在平台登錄，已送審核」，不顯示 A 的資料 |
| 2 | 有一筆疑似重複 | 平台營運者審核 | 決定只能是「同一產權」「不同產權」「退回補件」之一 |
| 3 | 判定同一產權，兩組織都有主要出租權源 | 營運者依文件判定 | 只保留一筆有效，另一筆改為「已失效」並通知該組織 |
| 4 | 判定為不同產權 | 之後再次比對 | 系統不再對這一組提示疑似重複 |
| 5 | 硬性撞號待審 | 使用者送簽該單位的合約 | 系統擋下送簽，顯示待審原因 |
| 6 | 軟性疑似重複待審 | 使用者送簽 | 系統得允許送簽 |
| 7 | 營運者開啟審核畫面 | 檢視案件 | 畫面只顯示判定所需欄位 |

技術考量：唯一鍵檢查跨組織。建議把唯一鍵放在平台層，只回傳「已存在」與審核單號。
電號、水號能否當分租單位的輔助鍵，見 Q19。

#### P0-08 出租權源鏈條

出租權源有三種，各有對應文件：

| 權源 | 文件 | 上游 |
|---|---|---|
| 所有權 | 第二類謄本 | 無 |
| 授權 | 授權書 | 所有權 |
| 轉租同意 | 轉租同意書 | 所有權或授權 |

狀態有四種：待驗證、已驗證、驗證失敗、已失效。

鏈條規則如下：

1. 出租人是所有權人時，主要出租權源為所有權。
2. 出租人受所有權人授權時，主要出租權源為授權。
3. 包租案件的出租人是包租業者，主要出租權源為轉租同意。
4. 上游未驗證時，下游不得改為「已驗證」。
5. 上游改為「已失效」時，系統必須把下游改為「已失效」，並通知下游出租人。
6. 轉租同意的出租人必須是營業項目含 H706021 且「已驗證」的執業主體。

文件規則如下：

1. 謄本由使用者自行申請並上傳。系統不得以自動化程式擷取電子謄本系統資料【中】。
2. 系統必須記錄謄本的取得時間。
3. 第二類謄本隱匿部分姓名與統一編號【高】。營運者只能部分比對，判定標準待法務（Q11）。
4. 謄本顯示信託登記時，系統必須記錄四項資料。依據為法務部 2026-09-21 書函【高】。
5. 四項為登記所有權人、信託關係人、信託登記狀態、取自信託契約的出租權限條款。
6. 系統與介面不得把「已驗證」描述為保證。「已驗證」只表示平台已比對文件。

送簽規則如下，待使用者拍板（Q2）：

1. 送簽前，租賃單位必須有一筆主要出租權源。
2. 主要出租權源為「待驗證」或「已驗證」時，系統得允許送簽。
3. 主要出租權源為「驗證失敗」或「已失效」時，系統不得允許送簽。
4. 主要出租權源為「待驗證」時，承租人端必須顯示「出租權源未驗證」。

| AC | Given | When | Then |
|---|---|---|---|
| 1 | 屋主上傳第二類謄本 | 營運者判定遮罩姓名與出租人相符 | 狀態改為「已驗證」，記錄判定人、時間、理由 |
| 2 | 謄本登記名義人與出租人不符 | 營運者判定 | 狀態為「驗證失敗」，系統要求補授權書 |
| 3 | 謄本顯示信託登記 | 使用者沒有上傳出租權限條款 | 狀態維持「待驗證」，系統列出缺件 |
| 4 | 轉租同意的上游所有權為「待驗證」 | 營運者核准轉租同意 | 系統不得核准 |
| 5 | 已驗證的所有權改為「已失效」 | 系統處理 | 下游轉租同意改為「已失效」，包租業者收到通知 |
| 6 | 轉租同意的出租人是「待驗證」的執業主體 | 送簽包租租賃合約 | 系統擋下送簽 |

| 8 | 已有一筆有效主要出租權源 | 使用者新增第二筆 | 系統要求先讓舊權源失效 |
| 9 | 使用者尚未同意個資告知 | 開啟謄本上傳頁 | 系統先顯示告知，同意後才開放上傳（P0-24） |

#### P0-09 案件與案件成員

案件是一個跨方流程的實例。Phase 1 有兩種案件：

| 案件 | 範圍 | 內容 |
|---|---|---|
| 租賃案件 | 一個租賃單位上的一段租賃關係 | 租賃合約、應收期別、鏡像帳分錄、押金台帳、點交、修繕、結算 |
| 委託管理案件 | 一位屋主與一家代管業者的委託關係 | 委託管理合約、委託標的清單、委託範圍 |

租賃案件的業務類型有三種：自管、代管、包租。
代管的租賃案件必須連結一個委託管理案件。
委託管理案件得連結系統內已完成的委託管理合約，或上傳既有紙本契約書。
撤回或拒簽後複製的新草稿，留在同一案件（ADR-0006）。
案件成員表 `case_members` 的欄位為 `case_id`、`party_id`、`relation`。
`relation` 有六種：出租人、承租人、委託人、受託人、所有權人、簽章人員。
權限由「關係加動作」決定。屋主得是執業主體組織內案件的成員，不必加入該組織。

| 動作 | 自管案件的出租人 | 代管案件的屋主 | 代管業者 | 包租業者 | 包租案件的所有權人 | 承租人 |
|---|---|---|---|---|---|---|
| 讀合約與帳務 | 是 | 是 | 是 | 是 | 限租期與狀態 | 限自己的案件 |
| 擬約與送簽 | 是 | 否 | 是 | 是 | 否 | 否 |
| 登錄入帳確認與押金分錄 | 是 | 否 | 限委託範圍 | 是 | 否 | 否 |
| 建立與處理修繕紀錄 | 是 | 是 | 限委託範圍 | 是 | 否 | 限報修 |
| 確認點交 | 是 | 是 | 是 | 是 | 否 | 是 |
| 對押金扣抵標示異議 | 否 | 否 | 否 | 否 | 否 | 是 |
| 讀屋主報表 | 自己的 | 自己的 | 自己產出的 | 否 | 自己的 | 否 |
| 發起移交 | 不適用 | 是 | 是 | 不適用 | 不適用 | 否 |

屋主出租給包租業者的租約，屬自管租賃案件，承租人為包租業者。
包租案件專指包租業者轉租給承租人的案件。
包租案件的所有權人不得讀承租人的個資。是否放寬待法務（Q15）。

| AC | Given | When | Then |
|---|---|---|---|
| 1 | 承租人是案件 X 的成員 | 讀取案件 Y | 系統拒絕 |
| 2 | 屋主是代管案件成員，不屬於代管業者組織 | 讀取案件 | 系統允許讀取該案件，拒絕讀取同組織其他屋主的案件 |
| 3 | 代管的租賃案件沒有連結委託管理案件 | 代管業者送簽 | 系統擋下，要求先連結委託 |
| 4 | 委託範圍不含押金管理 | 代管業者登錄押金分錄 | 系統拒絕 |
| 5 | 包租案件的所有權人 | 開啟轉租案件 | 只看到租期與狀態，看不到承租人姓名與聯絡資料 |
| 6 | 案件已結案 | 承租人登入 | 承租人得唯讀查看並下載已簽合約。保存期限待法務（Q16） |
| 7 | 合約被撤回並複製 | 系統建立新草稿 | 新草稿屬於同一案件 |

技術考量：RLS 政策必須同時允許「組織成員」與「案件成員」兩種存取路徑。
出現多層組織或文件級共享時，再評估 OpenFGA 或 SpiceDB。

#### P0-10 合約與電子簽署

合約由三層文件組成：主約、補充合約、附件。
條款快照（ADR-0005）、不可變衍生（ADR-0006）與狀態機維持現行設計。
Phase 1 的文件類型有兩種：租賃合約、委託管理合約。
每種文件類型有自己的範本、選用條款、附件、簽署人組合與簽署序列。

| 文件類型 | 附件 | 簽署人 |
|---|---|---|
| 自管租賃合約 | 設備附件 | 承租人、出租人 |
| 代管租賃合約 | 設備附件 | 承租人、出租人。§32 第 2 款不適用代管 |
| 包租租賃合約 | 設備附件、現況確認附件 | 承租人、包租業者、專任管理人員 |
| 經紀業居間的租賃合約 | 設備附件 | 承租人、出租人、不動產經紀人 |
| 委託管理合約 | 委託標的清單 | 委託人、受託人、專任管理人員 |

規則如下：

1. 狀態機必須支援依文件類型設定的簽署序列。
2. 自管租賃合約的現有狀態轉移測試必須全部通過。
3. 送簽必須啟用點點簽的簽署人驗證。可用方式由工程以 `dottedsign-api` MCP 確認（Q10）。
4. 簽署連結只對該案件的簽署人顯示。
5. 簽署完成導回網址必須是可公開存取的網域。
6. 正式環境的真實合約必須使用法務審閱版範本（Q9）。
7. 押金超過 2 個月租金時，系統顯示警告，依據為內政部範本【高】。是否改為阻擋待法務（Q20）。
8. 數位簽章須用經許可憑證機構的憑證，才推定為本人簽名【高】。點點簽的憑證資格由工程確認。

| AC | Given | When | Then |
|---|---|---|---|
| 1 | 代管案件的出租人為屋主 | 代管業者送簽 | 甲方簽署人為屋主，屋主收到點點簽 email |
| 2 | 包租租賃合約 | 包租業者送簽 | 簽署序列含專任管理人員，缺少時系統擋下 |
| 3 | 合約已送簽 | 承租人開啟簽署連結 | 承租人通過簽署人驗證後才能簽署 |
| 4 | 非簽署人開啟合約頁 | 載入頁面 | 系統不得顯示簽署連結 |
| 5 | 範本未標記為法務審閱版 | 在正式環境送簽 | 系統擋下。sandbox 不受限 |
| 6 | 押金超過 2 個月租金 | 儲存合約欄位 | 系統顯示警告 |
| 7 | 本需求完成 | 執行現有狀態機測試 | 自管租賃合約的狀態轉移測試全部通過 |

#### P0-11 委託管理合約

委託管理合約是新文件類型，由屋主與代管業者簽訂。
甲方為委託人屋主，乙方為受託人代管業者。
受託人必須是營業項目含 H706011 且「已驗證」的執業主體。
範本必須由法務依主管機關的委託管理定型化契約規範審閱（Q9）。
一份委託管理合約得涵蓋同一屋主的多個租賃單位。
附件為委託標的清單，逐列記錄租賃單位與委託範圍。
委託範圍至少分四項：收租、押金管理、修繕、點交。
系統必須依委託範圍限制受託人在租賃案件的動作（P0-09）。
受託人必須指派專任管理人員簽章（§32 第 1 款，P0-12）。
簽署序列建議為委託人、專任管理人員、受託人。順序待法務確認（Q12）。

| AC | Given | When | Then |
|---|---|---|---|
| 1 | 受託人為「已驗證」的代管業者 | 建立委託管理合約 | 系統帶入甲乙方與委託標的清單 |
| 2 | 受託人只有包租營業項目 | 建立委託管理合約 | 系統擋下，說明缺少 H706011 |
| 3 | 委託標的清單有 3 個租賃單位 | 合約完成 | 3 個租賃案件各自連結此委託管理案件 |
| 4 | 委託管理合約完成 | 受託人開啟租賃案件 | 只開放委託範圍內的動作 |
| 5 | 委託管理合約終止 | 到達終止日 | 受託人在連結案件的權限結束，系統提示屋主移交（P0-22） |
| 6 | 委託管理合約沒有專任管理人員簽章欄 | 受託人送簽 | 系統擋下 |

#### P0-12 簽章分流

租賃條例 §32 列六種文件，由租賃住宅服務業指派專任管理人員簽章【高】。
第 1 款不適用包租業務，第 2、3 款不適用代管業務【高】。

| §32 款次 | 文件 | 系統對應 | 代管業務 | 包租業務 |
|---|---|---|---|---|
| 第 1 款 | 委託管理契約書 | 委託管理合約 | 須簽章 | 不適用 |
| 第 2 款 | 租賃契約書 | 租賃合約 | 不適用 | 須簽章 |
| 第 3 款 | 現況確認書 | 現況確認附件 | 不適用 | 須簽章 |
| 第 4 款 | 點交證明 | 點交證明 PDF，P0-17 | 須簽章 | 須簽章 |
| 第 5 款 | 收據 | P1-06 | 須簽章 | 須簽章 |
| 第 6 款 | 退還證明 | P0-18 | 須簽章 | 須簽章 |

第 4 至 6 款的適用依本條文義推得，以原條文為準。

規則如下：

1. 「專任管理人員簽章欄」與合約當事人的簽署欄分開設定。
2. 簽章欄綁定執業人員紀錄，不以業者負責人身分帶入。
3. 綁定條件：證書種類為租賃住宅管理人員、已驗證、在職於該執業主體、專任旗標為是。
4. 業務類型由案件決定。系統依上表決定哪些文件必須有簽章欄。
5. 自管案件不產生 §32 簽章欄。
6. 經紀業居間的租賃合約，依經紀條例 §22 由經紀業指派經紀人簽章。
7. 經紀人簽章欄只能綁定證書種類為不動產經紀人的執業人員，不含經紀營業員。
8. §22 的其他文件類型列在 P1-09，清單待法務（Q17）。
9. 必要的簽章欄缺少時，系統不得送簽。
10. 每次簽章都寫入簽章紀錄。

| 執業主體 | 簽章當時的所屬主體 |
| 時間 | 點點簽回報的簽署時間 |
| 相對人同意紀錄 | 連結 P0-24 的電子簽署告知 |

|---|---|---|---|

#### P0-13 鏡像帳與入帳確認

鏡像帳是雙式分錄帳，只增不改。更正一律用沖銷分錄。
每筆分錄關聯一個業務事件 ID。
鏡像帳記錄的是收款帳戶的分錄副本，真相在銀行。
代管案件的租金得經代管業者帳戶，但收款帳戶持有人必須記錄。
入帳確認是系統內唯一的入帳事件。
入帳確認至少有下列欄位：事件 ID、案件 ID、金額、入帳日。
另有收款帳戶、持有人、`source`、證據檔。
Phase 1 的 `source` 只有 `manual` 與 `statement_file` 兩種。
事件名稱不得綁定信託帳戶，並加 `account_kind` 欄位。

規則如下：

1. 系統不得提供平台名下的收款帳戶（N1）。
2. 介面與文件不得用「信託」稱呼任何收款帳戶，依據為信託業法 §9②【高】。
3. 介面必須標示每筆入帳確認的來源：「使用者登錄」或「對帳檔」。
4. 外部檔案先落地到 inbox 表，以事件 ID 去重，再推進狀態。

| AC | Given | When | Then |
|---|---|---|---|
| 1 | 已完成合約有一筆應收期別 | 出租人登錄一筆 `manual` 入帳確認 | 系統產生借貸平衡的分錄，期別改為「已入帳」 |
| 2 | 分錄已寫入 | 任何角色修改或刪除該分錄 | 資料庫拒絕。使用者只得新增沖銷分錄 |
| 3 | 同一份對帳檔 | 匯入第二次 | 新增 0 筆分錄，系統回報重複列數 |
| 4 | 入帳金額小於應收 | 登錄入帳確認 | 期別改為「部分入帳」，差額保留 |
| 5 | 入帳金額大於應收 | 登錄入帳確認 | 超額記為預收租金，下一期由使用者選擇是否抵充 |
| 6 | 對帳檔有對應不到案件的列 | 匯入 | 該列進入待配對清單，不寫分錄 |
| 7 | 任何收款帳戶 | 顯示在介面 | 不出現「信託」字樣 |

技術考量：借貸平衡用 PostgreSQL 約束保證。觸發器禁止 UPDATE 與 DELETE。

#### P0-14 押金台帳

每個租賃案件有一本押金台帳。分錄類型有五種：約定、收取、扣抵、返還、移交。
押金台帳的分錄是鏡像帳中押金科目的分錄，兩者不得各自記帳。

規則如下：

1. 收取分錄必須記錄收款帳戶持有人。
2. 社宅代管案件的押金收款帳戶持有人不得是代管業者。依據為社宅委託管理範本 §8①十一【高】。
3. 一般代管案件的持有人為代管業者時，系統顯示警告並記錄確認者。待使用者拍板（Q3）。
4. 包租案件的出租人是包租業者，持有人為包租業者時不警告。
5. 扣抵分錄必須填原因與金額。使用者得連結點交紀錄或照片作為證據。
6. 押金返還沒有法定天數【高】。系統不得顯示法定返還期限，只顯示自退租點交起算的天數。
7. 所有權讓與時，押金隨之移交受讓人【高】。系統必須記錄移交分錄與通知承租人的時間。
8. 承租人得對扣抵標示異議。平台營運者不得介入協調（N3）。

| AC | Given | When | Then |
|---|---|---|---|
| 1 | 社宅代管案件 | 登錄收款帳戶持有人為代管業者 | 系統拒絕，並顯示範本依據 |
| 2 | 一般代管案件 | 登錄收款帳戶持有人為代管業者 | 系統顯示警告，記錄確認者與時間 |

#### P0-15 逾期提醒

#### P0-22 移交包

**優先級：P0。** v1 列為 P1。v2 升為 P0，理由有四：

1. P0-03 與 P0-04 會把經理人改為「已失效」並停權。沒有移交，進行中的案件無人能接。
2. BRD 8.1 把經理人更換列在 Phase 1 流程。甘特圖把移交包排在 M6 至 M9。
3. BRD R08 以移交包作為與仲介集團及銀行的差異化。
4. BRD 第 4 節的經理人 JTBD 列出移交包。

P0 的範圍是平台內逐案移交與匯出。匯入外部系統資料列為 P1-01。

移交包以租賃單位為單位，內容分六類：

| 類別 | 內容 |
|---|---|
| 權屬 | 出租權源與謄本取得時間 |
| 人 | 委託管理合約、現任承租人的租賃合約 |
| 屋況 | 點交紀錄、現況確認附件、設備附件 |
| 錢 | 押金台帳、預收租金、欠費、代收代付清單 |
| 實物 | 鑰匙、門禁卡的交付紀錄 |
| 行政 | 修繕紀錄、管委會窗口 |

六類由第一輪報告的附件清單反推【低】。業者更換時既有押金的處理規定沒有找到。

流程如下：

1. 屋主或舊受託人發起移交。執業主體「已失效」時，系統提示屋主發起。
2. 系統逐案產生移交包草稿，列出六類與缺項。
3. 屋主逐案確認，並選擇新受託人或改為自管。
4. 新受託人逐案確認接手，並指定生效日。
5. 生效日起，系統移出舊受託人，加入新受託人。

規則如下：

1. 新受託人必須已與屋主簽有委託管理合約，或已上傳紙本契約書。
2. 進行中的簽署任務必須先完成或撤回，才得移交。
3. 帳務為生效日的快照，附鏡像帳的 hash。
4. 押金收款帳戶持有人變更時，系統必須記錄移交分錄與證據。
5. 舊受託人保留移交包快照的唯讀副本。保存期限待法務（Q16）。
6. 缺項不中斷移交，但必須列在索引檔，並由屋主確認知悉。

| 1 | 屋主有 5 個代管案件 | 發起移交 | 系統產生 5 份草稿，逐案顯示缺項 |
| 2 | 新受託人沒有委託管理合約 | 確認接手 | 系統擋下，要求先建立委託 |
| 3 | 某案件有簽署中的任務 | 屋主確認移交 | 系統擋下該案，提示先完成或撤回 |

#### P0-23 稽核紀錄

稽核紀錄涵蓋下列事件：

- 判定：出租權源判定、重複審核判定、執業主體與執業人員驗證。
- 規則：專任阻擋與提示、簽章人員指派、狀態改為「已失效」。
- 權限：成員與權限變更、營運者存取組織資料、承租人登入、移交生效。
- 帳務：鏡像帳與押金分錄、報表產生、手動繳租提醒。

稽核紀錄只增不改。資料庫以觸發器禁止 UPDATE 與 DELETE，並使用獨立的寫入角色。
每筆紀錄以 hash chain 串接。chain head 每日錨定到平台外的時間戳記服務。
只靠 hash chain 擋不住有寫入權限者重算整條鏈【低】。
因此外部錨定是必要條件。
稽核紀錄與合約歷程分開。簽署舉證仍由點點簽 Audit Trail 承擔（ADR-0007）。

| AC | Given | When | Then |
|---|---|---|---|
| 1 | 營運者判定一筆執業人員驗證 | 判定送出 | 稽核紀錄有行為者、時間、前後狀態、理由 |
| 2 | 某資料庫角色有寫入權 | 對稽核紀錄執行 UPDATE 或 DELETE | 觸發器拒絕 |
| 3 | 每日排程 | 錨定 chain head | 系統保存外部服務的回執 |
| 4 | 有人重算整條鏈 | 執行驗證工具 | 工具比對外部回執，發現不一致並告警 |
| 5 | 營運者開啟組織資料 | 載入資料 | 系統寫入一筆存取紀錄，含工單號 |
| 6 | 組織管理員 | 匯出稽核紀錄 | 只含自己組織的紀錄 |

相依：外部錨定服務選型（Q21）；保存期限（Q16）。

#### P0-24 告知與同意紀錄

電子簽章法 §5 要求取得相對人同意。推定同意得以反證推翻，平台必須保存同意紀錄【高】。
蒐集身分證、謄本與證書，必須有特定目的與必要性，並事先告知。
依據為個資法 §5、§6、§8、§19、§20。
每份告知文字都有版本號。系統記錄告知對象、時間、版本、同意或反對。

告知類型如下：

| 告知 | 對象 | 時點 |
|---|---|---|
| 電子簽署告知 | 每位簽署人 | 送簽前 |
